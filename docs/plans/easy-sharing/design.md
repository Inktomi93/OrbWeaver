# Easy sharing: one step from a single box to friends on the internet

## Goal

A host with no shell skill, on bare metal or Docker, takes one step and friends outside the LAN join a multi-human room over a free relay, with live streaming intact and every existing security control still on.

## Shape

Not yet built. Section 1 re-derives the brief against the tree. Section 2 is the transport finding with the probe evidence. Section 3 surveys every free relay. Section 4 is what the field does. Section 5 is the security posture a share must satisfy and what the app enforces on its own. Section 6 is the UX. Section 7 is the friend's side of a relay restart. Section 8 ranks the backends. Section 9 orders the build legs. Every claim marked "unverified" was not reproduced here.

### 2. The transport finding

Method. Two origins on private loopback ports, never the dev stack. Origin A: a `node:http` server with `/sse` (`text/event-stream`), `/jsonl` (`application/jsonl`) and `/text` (`text/plain`) on GET and POST, one chunk every 500 ms for 20 chunks, plus a hand-rolled RFC 6455 WebSocket at `/ws` on the same clock. Origin B: this checkout's server in `AUTH_MODE=local` with `ORB_ENV_NO_FILE=1`, a throwaway database under `.cache/` and `ALLOWED_HOSTS` set to the tunnel host. Relay: `pnpm dlx untun@latest tunnel http://localhost:<port>` (cloudflared 2026.7.2 downloaded to `/tmp/node-untun/`, run with `--no-tls-verify`). Client: a node script recording every body chunk's arrival; the spread is last arrival minus first. A streamed body spreads about 9.5 s; a buffered body arrives as one chunk after the server closes.

| Case | Direct | Quick tunnel, run 1 | Quick tunnel, run 2 |
| - | - | - | - |
| GET `/sse` | 20 chunks, first 542 ms, spread 9508 ms | 1 chunk at 10468 ms, spread 0 | 1 chunk at 10461 ms, spread 0 |
| POST `/sse` | 20 chunks, first 504 ms, spread 9509 ms | 28 chunks, first 597 ms, spread 9504 ms | 26 chunks, first 564 ms, spread 9507 ms |
| GET `/jsonl` | 20 chunks, first 503 ms, spread 9506 ms | 1 chunk at 10086 ms | 1 chunk at 10066 ms |
| POST `/jsonl` | 20 chunks, first 502 ms, spread 9508 ms | 20 chunks, first 570 ms, spread 9507 ms | 20 chunks, first 582 ms, spread 9505 ms |
| GET `/text` | 20 chunks, first 502 ms, spread 9505 ms | 1 chunk at 10109 ms | 1 chunk at 10102 ms |
| WebSocket `/ws` | open at 5 ms, 20 frames, spread 10005 ms | open at 288 ms, 20 frames, spread 9865 ms | open at 234 ms, 20 frames, spread 9887 ms |

Against the real server, `stream.connect` as the browser sends it (GET, `Accept: text/event-stream`, session cookie), then `stream.attach` for the `user` room after one second, reading for 35 s:

| Step | Direct | Quick tunnel |
| - | - | - |
| login | 200, cookie `orb_session_insecure` | 200, cookie `__Host-orb_session` |
| response head | 200 `text/event-stream` at 21 ms | 200 `text/event-stream` at 227 ms |
| `connected` frame | 22 ms | never |
| `attached` control frame | 1039 ms | never (the attach itself answered 200) |
| server pings | 16.0 s and 31.0 s | never |
| body bytes in 35 s | every frame | zero |
| POST `stream.connect` | `METHOD_NOT_SUPPORTED`, http 405 inside a 200 SSE body | same |

Reading. The quick tunnel holds every GET response body until the origin closes it; content type does not matter. POST bodies and WebSocket frames pass as produced. Every orbweaver live surface is a GET SSE, so through a quick tunnel a friend sees no typing, no turn, no notification and no presence. The inactivity timer that would reconnect a silent socket is client-side and is armed by the `connected` frame's `reconnectAfterInactivityMs` (the installed `@trpc/server` consumer stores the options when that frame arrives); through a quick tunnel that frame never arrives, so the room stays frozen until the tab reloads or the relay drops the connection. Cloudflare documents WebSockets on every plan; the probe agrees.

The three ways to make the streams survive, priced against this tree:

(a) POST subscriptions. Server: `fetchRequestHandler({ allowMethodOverride: true })` in `packages/server/src/entry/app.ts`. tRPC then accepts POST for subscriptions and reads the input from the body; GET keeps working, so `tests/e2e/support/sse.ts` is untouched. Client: `httpSubscriptionLink({ url, EventSource: PostEventSource })`, where `PostEventSource` is a class in a new file post-event-source.ts beside `packages/client/src/data/bus/use-orb-socket.ts` that satisfies the consumer's `EventSourceLike.Instance` contract:

- `new (url, init)`, the instance constants `CONNECTING`, `OPEN` and `CLOSED`, `readyState`, `addEventListener` and `removeEventListener` for `open`, `error`, `message` and every named event (`connected`, `ping`, `serialized-error`, `return`), `close()`, and a `MessageEvent` carrying `data` and `lastEventId`.
- The request: it moves the `input` query parameter into a JSON body, sends `POST` with `Content-Type: application/json` (the mount's `trpcJsonOnly` middleware answers 415 to any other POST content type), `Accept: text/event-stream`, the CSRF header and same-origin credentials, and parses the body with the SSE grammar.
- Terminal answers: a non-2xx status, a 204, or a response whose content type is not `text/event-stream` sets `readyState` to `CLOSED` and fires `error` with no reconnect. The consumer turns an `error` into a stream error only when `readyState` is `CLOSED`; otherwise it reports `connecting`.- Reconnect: when the body ends or the fetch fails, it fires a plain `Event` named `error` with `readyState` at `CONNECTING`, waits the last `retry:` value or the browser default, and reopens. The event carries no `data`, because `packages/client/src/features/chat/hooks/use-guided-actions.ts` treats a `connecting` error that carries a tRPC error shape as a server fault and rejects. It never reconnects after `close()` or after the `return` event, which the consumer answers by closing the source.
- Resume: a native EventSource sends `Last-Event-ID` on its own reconnect and the consumer also re-sends the last id through the input; no procedure here resumes by it. `stream.connect` resumes each room from the cursor `stream.attach` carries in `sinceSeq`, and `chat.impersonateStream` is one-shot.

Cost: one class, one link option, one server option, and the mirrors in the test plan. The CSRF middleware in `packages/server/src/transport/trpc/trpc.ts` checks the header for mutations only, so nothing tightens or loosens; a POST body also keeps the `socketId` out of proxy logs.

(b) tRPC `wsLink` over a WebSocket. The probe says a quick tunnel passes frames. Cost: a `ws` dependency and `@trpc/server/adapters/ws`, an upgrade hook on `@hono/node-server`, a second authentication seam at the upgrade (cookie read, `Origin` check, no CSRF header), a second stub shape for every client CT, and the SSE reconnect and cursor code kept anyway. `docs/adr/0118-all-server-client-streaming-rides-one-multiplexed-sse.md` rejects `wsLink` for the same reasons. Rejected.

(c) Detect a tunnel host and switch transport only there. `location.hostname` ending in `.trycloudflare.com` picks (a), everything else stays native. Two transports mean two CT stub shapes and defects that appear only on the shared link; the POST class also lets a subscription carry the ngrok bypass header. Rejected as the default; the fallback if the always-on CT blast radius is refused.

Decision: (a), always on. Leg T in section 9. It lands before any share surface, because a share that ships a frozen room is worse than none.

### 5. Security posture

What must be true before a link goes out, each with its home:

| Condition | Why | Home |
| - | - | - |
| a login mode, `local` or `oidc` | a relayed request is never the owner, so single-user answers 401 to every visitor | `packages/server/src/infra/auth/forwarded.ts` |
| `BIND_HOST=127.0.0.1` when the box switches from `just-me` | in production `local` binds every interface (`packages/server/src/foundation/env/bind.ts`), which would open the LAN over plain http beside the relay; a box that already answers to its network keeps its bind | the key writer (leg R) owns the key and gains a delete value (`null` in `tooling/src/stack/lib/setup-plan.ts` means leave the line); the wizard's `network` answer deletes it; the launcher restates it |
| the owner is claimed (`local` only; `oidc` has no first-run route) | the relay must not start before the owner holds a password, or the tunnel exposes an unclaimed box; the first-run claim is loopback-only and one-shot, so friends can never claim it through the tunnel | the existing `POST /api/auth/first-run` at the local origin (`packages/server/src/entry/http/auth-routes.ts` lines 435-446 and 663; `packages/server/src/entry/boot/seed-owner.ts` lines 14-19); no new setter; `LOCAL_INITIAL_PASSWORD` stays the headless seed, untouched. A `SHARE_RELAY=quick` relay refused at boot starts on the claim landing, not the next boot: the claim is the server's own route, so the share controller starts the relay right after `setOwnerPassword` succeeds, with no restart and no polling |
| `localMultiUser` on | invites and `/join/:token` are 404 without it | `MULTI_HUMAN_CAPABLE` in `packages/server/src/entry/app.ts` |
| `discreetLogin` on | the sign-in page otherwise shows the default handle `owner` (`defaultHandle` in `packages/server/src/entry/http/auth-meta.ts`), and hiding it turns one unknown into two | the `discreetLogin` app setting (`packages/contracts/src/settings/index.ts`) |
| the relay host allowed | the Host check refuses every unknown name and has no off switch | `packages/server/src/entry/http/host-allowlist.ts`, the relay registry of leg H |
| an account per friend | `redeemInvite` needs a principal; `local` has no self-registration | `packages/server/src/transport/trpc/routers/admin.ts`, leg J |
| the session cookie is `Secure` | the relay sends `X-Forwarded-Proto: https` from a loopback hop, which is the trusted-hop rule | `packages/server/src/infra/auth/transport.ts` |
| per-visitor rate limits | `clientIp` reads `X-Forwarded-For` behind a trusted hop, so the throttles key on the visitor | `packages/server/src/infra/network/ingress.ts`, `packages/server/src/entry/rate-limit-gate.ts` |
| diagnostics recorders off | prompts and transcripts must not sit behind a public link | the boot disclaimer's warnings |

What the share surface enforces on its own, in order: refuse to start under single-user and name the fix; refuse to start the relay while the owner is unclaimed and send the host to the first-run setup at the local origin; turn `localMultiUser` and `discreetLogin` on with one confirmation; register the relay host the moment the relay reports it and drop it when the relay stops; show the URL with the warning sentence; on relay death show "down", restart, and say when the URL changed. Stopping a share ends the relay; sessions minted through it stay valid until they expire, so the panel offers "sign everyone out" through `admin.revokeUserSessions` (`packages/server/src/transport/trpc/routers/admin.ts`) per member, which the socket eviction follows.

The residual risk to state in the panel: a quick-tunnel URL is public and unguessable, the sign-in page is the only thing a stranger reaches, the login throttle is per visitor address, and the per-handle throttle (`packages/server/src/entry/http/auth-routes.ts`, three times the per-address cap) is the ceiling against a guesser who rotates IPv6 addresses.

### 6. The UX

Bare metal, `pnpm start --share` (with `pnpm share` as an alias script). The launcher owns the child env (`tooling/src/stack/lib/start-plan.ts`). The share flag adds two steps before the spawn: restate every `.env` value on the child env with `ORB_ENV_NO_OVERRIDE=1`, the `portOverrideEnv` shape, then set `AUTH_MODE=local`, `SHARE_RELAY=quick` and, when the file says `just-me`, `BIND_HOST=127.0.0.1`; spawn the server. The launcher asks no password question: while the owner is unclaimed the server refuses to start the relay and prints "open `http://localhost:<port>` on this machine and finish setup first" (section 5). The server starts the relay itself at boot (leg S), registers the host in its relay registry (leg H) and prints the URL with the warning sentence and "invite friends from a room's invite dialog". `ALLOWED_HOSTS` is never written for a relay, so a relay restart with a new name cannot hit a 421. `localMultiUser` and `discreetLogin` are settings, not env, so the launcher cannot flip them; the panel does, once.

In-app, the Share card in Admin > Multi-user beside the read-only posture panel (`packages/client/src/features/user-admin/components/governance-sections.tsx`). Owner-only. It shows the preconditions of section 5 as rows, each with its fix. The owner-password row sends the host to the existing first-run screen, never a new setter. The mode row writes `AUTH_MODE=local`, and `BIND_HOST=127.0.0.1` when the box was `just-me`, through the key writer (leg R), then restarts the server through the launcher supervisor. Under an unsupervised launch the row shows `pnpm start --share`; in a container, the `docker/orbweaver.local.env` lines and `docker compose up -d`. When every row is green, "Start sharing" calls `share.start`; the server spawns the relay, registers the host, and the card shows the URL, a copy button, the relay kind, the count of live sockets from `liveSocketCount`, "Stop sharing", "sign everyone out" and an "Invite someone to a room" link that opens the existing per-room invite dialog; there is no new invite UI. An in-app share is not persisted: a server restart ends it, the card returns to `off`, and the owner starts it again; only the launcher's `SHARE_RELAY=quick` restarts a relay on its own. The invite dialog (`packages/client/src/features/chat/components/invite-dialog.tsx`) copies `https://<host>/join/<token>`, never a `localhost` link; invites are per room and are made there.

The friend. Opens the URL, sees the sign-in page, signs in with the handle and password the host made, lands on `/?join=<token>` and runs the preview-then-confirm invite flow; today the token does not survive the sign-in (section 1). That is three secrets to hand over and one host action in Admin > Users first. The one-step version is leg J: `allowSignup` on the invite lets `/join/<token>` provision the account in the transaction that consumes the invite. Leg J covers `oidc` and `forward-header` with the same dialog and redeem (owner fork 4).

Docker. A quick-tunnel overlay `docker/compose.quick-tunnel.yaml` runs the `cloudflare/cloudflared` image with `tunnel --url http://orbweaver:8788 --metrics 0.0.0.0:2000` and no token. The app reads `http://cloudflared:2000/quicktunnel` when `SHARE_RELAY=sidecar` and `SHARE_TUNNEL_METRICS_URL` are set, retries until the sidecar answers, and registers the hostname in the relay registry; the sidecar is trusted like the named-tunnel sidecar. The login mode and password lines are the existing recipe in `docker/README.md`. In-app "Start sharing" in a container shows the compose command instead of spawning (Rejected: no relay binary in the image).

Relay death: section 7. The state machine is `off`, `starting`, `up(url)`, `down(reason)`, with a bounded restart.

### 7. The friend's side of a relay restart

When a quick tunnel restarts, the hostname changes, and every friend pays for it. The triggers: the relay process dies, the host stops and starts sharing, or the server restarts (a supervised respawn, the admin `restart`, a crash), because the relay is the server's child and starts again with the server:

| Effect | Cause | What the design does |
| - | - | - |
| every friend is signed out | the `__Host-` cookie is bound to the old host, so the new origin has no cookie | say it on the card; the friend signs in again at the new URL |
| every friend's local state is gone | per-origin storage (appearance choices, drafts, the persisted stores) belongs to the old host | say it on the card; server-side settings survive |
| open tabs stop with "Lost the live connection" | the dead host answers a non-2xx, which the `PostEventSource` class treats as terminal, so the socket fault notice (`packages/client/src/data/bus/use-orb-socket.ts`) shows; the tab retries only while the name fails to resolve | the old tab must be closed; the app cannot redirect a page it no longer serves |
| the new URL must reach friends out of band | the relay name is not knowable in advance, and the old host cannot answer | the card shows a large "the link changed" notice with the new URL and a copy button; an invite stores only its token hash and the host is `location.origin` at copy time, so the card says "old links still work if you replace the host with the new one" and offers revoke and re-mint |
| in-flight turns are lost on the friend's screen | the socket that carried them is gone | the turn itself finished on the server; the friend's next load shows it |

The card carries one standing sentence above the URL: for anything longer than a session, use a named tunnel, whose name survives a restart.

### 8. Ranked recommendation

1. Zero-account default: a Cloudflare quick tunnel through the `cloudflared` npm package (`Tunnel.quick()`, `url` and `connected` events, `bin` for the binary path, MIT; its `install` and postinstall are not used). Cost: a binary download on first share, with the license line printed. The controller pins the version and verifies a checksum (leg S). Precondition: leg T.
2. Tailscale Funnel: dropped by owner ruling. A Tailscale user can run `tailscale funnel` against the port and add its name to `ALLOWED_HOSTS`.
3. A named Cloudflare Tunnel stays the documented path for a host with a domain; the overlay exists.
4. ngrok's SDK is the only binary-free path, but the interstitial, the 1 GB month and the published origin IP keep it off the default list; it fits as a later backend behind the same state machine.

The share surface uses the quick tunnel only. Owner fork 3.

### 9. Build legs

- Leg T, transport: `allowMethodOverride` on the mount, `PostEventSource`, the link option. Lands first and alone.
- Leg L, launcher: `--share` on `pnpm start` and the `share` script; the child env of section 6. No password question: the owner is claimed through the existing first-run screen. The relay itself is the server's (leg S).
- Leg H, the relay registry: `hostAllowlist` takes a reader that unions the env list with a server-owned set that only the relay controller writes; exact names, cleared on stop. It is the one owner of a relay host on every path (fork 2).
- Leg R, restart and key writer, not yet built. `pnpm start` becomes a supervisor. On every respawn it re-reads `.env` and rebuilds the whole spawn plan, because two overlays are computed from the file: `singleUserFallbackEnv` in `tooling/src/stack/lib/start-plan.ts` adds `AUTH_FALLBACK=owner` under single-user, which `packages/server/src/foundation/env/index.ts` refuses at boot once the mode is `local`, and `portOverrideEnv` restates the file's values with `ORB_ENV_NO_OVERRIDE`, which would keep the old mode. The loop wraps only the server run; the setup pass runs once, before the loop. Signal handlers are registered once and forward to the current child, because `forwardSignalsTo` in `tooling/src/_shared/proc.ts` adds a listener per call. The admin `restart` procedure is owner-only, needs an explicit confirm, is rate limited and single-flight, refuses when no supervisor started the server, closes the app and exits with the restart code. In Docker there is no restart path (section 6 and Rejected). The key writer is a pure `@orb/kit` module in the `applySetupValues` shape; the file write stays in the server's restart verb and the tooling ops (the `packages-no-tooling` gate). The server writes only the keys the setup wizard owns plus `BIND_HOST`.

- Leg J, one new flag on the existing room invite, never a parallel system. The reused machinery: the mint dialog (`packages/client/src/features/chat/components/invite-dialog.tsx`; its defaults are expiry never and `maxUses` unlimited, lines 226-227 render them); `createInvite` with `resolveExpiresAt` and `resolveMaxUses`, where an explicit `null` means never or unlimited and the default TTL is 48 hours (`packages/server/src/domain/chat/verbs/invites.ts` lines 84-118); the hashed token (verbs line 166); `revokeInvite` (`packages/server/src/transport/trpc/routers/invites.ts` line 110); `GET /join/:token`, 404 unless `multiHumanCapable`, else 302 to `/?join=<token>` (`packages/server/src/entry/http/join.ts` lines 19-23); the SPA handoff and join dialog (`packages/client/src/data/join-token.ts`, `packages/client/src/routes/app-root.tsx` lines 30-35 and 122, `packages/client/src/features/chat/anchors/join-invite-dialog.tsx`); `previewInvite` and `redeemInvite` (routers/invites.ts; verbs lines 209-211 and 240-249); and `redeemInviteAtomic`, which already closes the expiry and `maxUses` race (verbs lines 4 and 243; `packages/server/src/domain/chat/persistence/invites.ts` line 70). Today under `oidc`, an existing user opens the link, `requireAuthed` sends them to `/login` (the token drops there), they sign in at the IdP and land on `/`, and the join dialog's `redeemInvite` seats them through `redeemInviteAtomic`, which checks expiry, uses and targeting. The delta, `allowSignup`: one column on the invite row. When it is set, the mint dialog and `createInvite` force a finite expiry and a finite `maxUses` and refuse a target. `redeemInviteAtomic` is extended to run one user-insert statement in the same transaction, before the seat; there is no second redeem and chat persistence never inserts users. The owning domain supplies the statement, the `revokeAllForUserStatement` shape (`packages/server/src/entry/compose/admin.ts` line 112): `admin`'s `createUser` rules for `local`, the sessions domain's `provisionIdentity` rules (collision deny, owner adoption, role from groups, subject binding) for `oidc`; every check reruns inside the transaction. Per mode:
  - `local`: the join dialog offers a signed-out visitor a handle and a password. Its confirm calls the extended redeem, which runs `admin`'s user-insert statement with the password hash and consumes a use in the one transaction. The signed-out route takes the login route's guards in order: the CSRF header, the body cap, the per-address and per-handle throttles before any hashing. It reuses `createUser`'s handle validation and refuses the owner seed handle and every `OWNER_HANDLES` name (`packages/server/src/entry/boot/seed-owner.ts` line 87). The card states the cost of a leaked link: every minted account owns an AI-turn bucket, so uses and expiry are the spend cap. The token survives the sign-in: the `/login` redirect carries `join`, and `goHome` returns to `/?join=<token>`.
  - `oidc`: the delta from today's flow is three steps, and no password is ever minted. First, the login page stashes the raw token in `sessionStorage` and passes only its hash to `GET /api/auth/oidc/login` (`packages/server/src/entry/http/auth-routes.ts` line 784); the hash rides the transaction row (`OidcTransaction`, `packages/server/src/infra/auth/contract.ts` lines 42-48; server-side, single-use and browser-bound by the binding cookie, auth-routes lines 261-273). Second, the callback (auth-routes line 838) never provisions from an invite. It runs `provisionIdentity` as today, with the group gate first (`packages/server/src/domain/sessions/verbs/provision-identity.ts` lines 436-446). Only when the identity is unknown, the JIT gate is closed (provision-identity lines 362-372) and the hash names a valid `allowSignup` invite, the callback, which has already consumed the transaction and cleared the binding cookie as today (auth-routes lines 272 and 840), writes a separate pending record that `consume` never returns. The record holds the resolved subject, handle, email and groups, the invite hash, and the hash of a fresh random secret, with a ten-minute TTL from the callback. The secret rides only a new HttpOnly pending cookie pair (`__Host-` on https, as the binding cookie) with the same TTL, never a URL; `state` stays single-use and is never a credential. It redirects to `/`. Third, the join dialog shows the preview to the pending identity. Its confirm hashes the pending cookie and finds the record by that hash, never by `state` or the invite hash, then runs the extended redeem, which consumes the pending record, runs the sessions domain's user-insert statement, consumes a use and seats the member in the one transaction; the cookie is cleared and the session mints after it. That closes two holes. One single-use link cannot provision unlimited identities, and a forced login with a planted `join` creates nothing without consent. `OIDC_REQUIRE_APPROVAL` (owner fork 7): an invite never counts as approval, so the confirm provisions the row disabled and mints no session; the confirm is an API call, so the join dialog itself says "ask the host to approve you in Admin > Users, then open your invite link again". The invite must outlive the approval (the 48-hour default TTL above).
  - `forward-header`: identity is the proxy's. The seam provisions every proxied identity with JIT allowed and no approval (`packages/server/src/entry/auth/seam.ts` lines 210-217; `allowJitProvision` undefined means allowed, provision-identity line 365), so a proxy user with no account gets one on the first request and the invite binds seat and room to that identity through the unchanged dialog and `redeemInvite`. A friend the proxy does not admit never reaches the app; the host grants access at the proxy first, and the card says so. `createInvite` refuses `allowSignup` in this mode, because JIT is always on here, and under `single-user`.
  - `single-user`: sharing is refused (section 5) and invites stay 404 (`MULTI_HUMAN_CAPABLE` in `packages/server/src/entry/app.ts`).

Owner forks, each with the default this plan takes: (1) ruled by the owner: the Share card switches the mode through the key writer and a supervised restart (leg R), not in-process, which keeps `docs/adr/0255-network-and-auth-modes.md` (the mode stays an env var); (2) ruled by the owner: the Host allowlist gains one server-owned relay registry, exact names only, no operator off switch, and it is the only home of a relay host on the launcher, in-app and Docker paths; (3) ruled by the owner: the quick tunnel only, and Funnel is dropped; (4) ruled by the owner: leg J ships, clean under `oidc` and `forward-header`, so it is one path per mode with one redeem chokepoint; (5) ruled by the owner: POST subscriptions are always on, not tunnel-only; (6) ruled by the owner: the server's relay controller downloads a pinned cloudflared and verifies its checksum on first share, rather than asking the host to install cloudflared; the npm package supplies the path and the process wrapper, never the download; (7) ruled by the owner: a valid share-link invite does not count as approval under `OIDC_REQUIRE_APPROVAL`; the account waits in Admin > Users (leg J).

## Rejected

- WebSocket transport (`wsLink`): a second auth seam, a second CT stub shape, and the SSE lifecycle code kept anyway; the ADR already rejects it.
- A tunnel-only transport switch: two transports and defects that appear only on the shared link.
- An in-process auth-mode switch behind the Share button: the mode stays env, and a supervised restart re-validates the whole config at one boundary.
- `.env` hot reload in the style of Marinara's env watcher: two sources of truth beside the DB-backed Admin config, and security keys would change under live sessions; the env is validated once at boot.
- A relay host in `ALLOWED_HOSTS`, exact or as a `.trycloudflare.com` suffix: the list is frozen at boot, so a relay restart answers 421, and the suffix admits every quick tunnel anyone runs; the relay registry admits one.
- A Docker restart verb: the root filesystem is read-only and the env is the host's files, so there is nothing the server could write.
- `untun` as the dependency: a CLI wrapper over the same fork with `--no-tls-verify` added by default and no process handle.
- ngrok as the default: the interstitial, the 1 GB month, and the host's IP in the URL.
- localtunnel, bore, Pinggy's ssh form, port mapping: a password page that publishes the host's IP, no TLS, or no library path.
- A relay binary inside the Docker image: the sidecar overlay is the container-native shape and keeps the image small.
