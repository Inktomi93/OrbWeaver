## AGENT-TOOLING-01 — retain P1 / behavior-defect / R5

Retain the finding, but narrow its wording to the implemented hook contract: **an unanchored raw-command self-exemption converts any command containing `tool-guard.mjs`, `guard-replay.mjs`, or `transcript-census.mjs` into an explicit PreToolUse `allow`, before every destructive and hard-floor rule.** `SELF_EXEMPT` is an unanchored regex (`.claude/hooks/tool-guard.mjs:213`) and `classify` returns before quote/heredoc blanking and the hard floor (`.claude/hooks/tool-guard.mjs:544-554`). All non-deny/ask/defer results, including `pass`, become `permissionDecision:"allow"` (`.claude/hooks/tool-guard.mjs:843-885`), and the hook is registered for every Bash call (`.claude/settings.json:3-14`).

Safe classifier-only probes (the payload strings were never executed) returned `pass/self-exempt` for each of: the legitimate guard invocation, `git stash # tool-guard.mjs`, `echo 'tool-guard.mjs' && git stash`, and a `curl | bash` shape with that trailing comment. A real stdin/stdout hook-protocol probe for the `git stash` comment emitted `{"hookSpecificOutput":{"permissionDecision":"allow"}}`. This is R5: it exercises the registered hook's actual protocol, not an in-process copy.

The existing test table contains only two genuine self-tool commands (`tests/tooling/tool-guard.int.test.ts:219-220`) and asserts the table generically (`:223-237`); it has no must-bite comment, quoted-argument, or earlier-compound-stage case. Its current contract tests do prove ordinary `allow` behavior (`:325-348`) but do not mitigate the bypass.

Later host policy does not restore this project-level control. The project settings define allow rules only (`.claude/settings.json:55-129`) and no deny/ask rule. Claude Code's current hook reference says PreToolUse `allow` skips the permission prompt, while separate deny and ask rules still evaluate; therefore an unseen user/org deny-or-ask policy could still block a command, but no such policy is evidenced in this snapshot. The host behavior confirms the severity of the hook defect rather than downgrading it: the configured guard emits authorization where its own hard floor was supposed to refuse it. This is a P1 broken enforcement boundary under the audit rubric, not a production application auth bypass.

Minimal safe fix/test shape: remove the global raw-string early return. Parse and blank first, then exempt only a sole command whose executable and resolved script operand are one of the guard's own validation tools; compound commands must continue through every rule. Add classifier and wire-protocol must-bite rows for a trailing comment, a quoted filename argument, and a filename in an earlier `&&` stage, alongside a must-pass genuine `node .claude/hooks/tool-guard.mjs --classify-batch` invocation. Rerun the 12-test file.

## DEPLOCK-01 — do not retain as P1; reclassify to bounded P2 candidates

Do not state “12 highs = P1” or that all high records are production-reachable. `pnpm audit` establishes vulnerable resolved versions, not an application exploit path. The current evidence supports two bounded P2 upgrade candidates, neither a proven exploit:

- **sharp@0.34.5 — P2 / operability-gap / medium exploit confidence.** An authenticated caller can upload a raster asset through the auth/CSRF/body-cap boundary (`packages/server/src/entry/http/upload.ts:95-129`); an owner can then request a width variant, which reads that original and calls `imageTransform` (`packages/server/src/entry/http/blob.ts:103-126`, `packages/server/src/domain/assets/verbs/resolve-variant.ts:20-42`). Composition binds the real adapter (`packages/server/src/entry/compose/services.ts:294-317`), whose transform decodes bytes with sharp (`packages/server/src/infra/image/index.ts:115-136`). The current sharp advisory says processing untrusted input before 0.35.0 is affected and names 0.35.0 as the fixed floor ([GHSA-f88m-g3jw-g9cj](https://github.com/advisories/GHSA-f88m-g3jw-g9cj)). This is a real authenticated untrusted-image decoder surface, but no malicious image was executed and no compromise was proven; P1 would overstate that evidence.
- **pdfjs-dist@6.1.200 — P2 bounded candidate / operability-gap / low exploit confidence.** An authenticated caller can upload document bytes through `POST /api/databank/upload` (`packages/server/src/entry/http/upload.ts:133-162`); the domain then calls `extractText` synchronously (`packages/server/src/domain/databank/verbs/upload.ts:29-42`), dispatching `application/pdf` to `loadPdf` (`packages/server/src/infra/extraction/formats.ts:13-39`) and `getDocument` (`packages/server/src/infra/extraction/loaders/pdf.ts:65-88`). The published advisory's arbitrary-JavaScript condition is PDF.js scripting enabled in a hosting-domain context without a prohibiting CSP ([GHSA-hq66-cqwq-w95j](https://github.com/advisories/GHSA-hq66-cqwq-w95j)); this code instead uses the server-side, DOM-less legacy build for text extraction only (`packages/server/src/infra/extraction/loaders/pdf.ts:1-9`). Untrusted bytes reach the package, but the advisory's browser-context exploit preconditions are not proven here. Upgrade it, but do not call it a proven P1 RCE/XSS path.

The remaining high records are not proven reachable from untrusted application input:

- **adm-zip** is production-transitive only through `@huggingface/transformers → onnxruntime-node`; the cache does load models (`packages/server/src/infra/providers/backends/local-light/model-cache.ts:202-240`), but composition supplies fixed local-light model defaults (`packages/server/src/entry/compose/services.ts:366-370`). No normal untrusted upload or caller-chosen archive path was established. Treat it as a supply-chain maintenance candidate, not a user-input exploit finding.
- **fast-uri** and **ip-address** are production-transitive through `agent-sdk → @modelcontextprotocol/sdk`; there is no direct application import. The live terminal channel builds an in-process SDK MCP server (`packages/server/src/infra/providers/backends/agent-sdk/terminal-tools.ts:107-127`). The only code that accepts external stdio/SSE/HTTP MCP servers is the dormant agent-turn route (`packages/server/src/infra/providers/backends/agent-sdk/agent-runner.ts:26-30,143-145`); structural callers found no production caller beyond the adapter. Thus the `ip-address` SSRF/trust-boundary advisory ([GHSA-mwp4-54f8-5fhr](https://github.com/advisories/GHSA-mwp4-54f8-5fhr)) and the three fast-uri advisories are unproven for this app's untrusted input.
- **brace-expansion** is lint/Stryker transitive only, and **nanoid** is Vite/Playwright/Vitest tooling transitive only. They are development paths, not release-server attack surfaces. Their repeated dependency paths must not be counted as independent vulnerabilities.

The narrow behavioral evidence is current but non-exploitative: `tests/server/infra/extraction/loaders/pdf.int.test.ts` (5), `tests/server/domain/databank/verbs/upload.int.test.ts` (7), and `tests/server/infra/image/index.int.test.ts` (12) all passed, establishing normal decode/upload wiring (24 tests total). This does not prove an advisory exploit or compensate for it.

Coordinator wording: replace DEPLOCK-01 with “online pnpm audit reports 12 high advisory records, representing seven package families and ten distinct GHSAs; source review establishes a bounded authenticated untrusted-image sharp surface and an untrusted-PDF server-extraction candidate, both P2 pending upgrade. The remaining high records are dev-only, duplicate advisory families, or unproven transitive paths.” Route dependency upgrades to manifest owners, then rerun online `pnpm audit --json`; do not claim exploitability until an advisory-specific abuse path is safely demonstrated.
