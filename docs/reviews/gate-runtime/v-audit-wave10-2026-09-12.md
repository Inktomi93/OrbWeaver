## Durable lessons proposed (the orchestrator owns the memory write)

**1.** `- [sibling A/B beats a cut](family-sibling-ab-beats-a-cut.md) — two modules in ONE family answering
the same identity question two ways IS the experiment; run the byte-identical fixture through both.`

> When a family contains both a shared-reader consumer and a hand-rolled one, the strongest available
> receipt is not a cut — it is the SAME fixture through both modules. `no-raw-id` (private
> `getSymbol().getDeclarations()` walk) came back blind to a one-hop re-export door while
> `no-mint-via-cast` (shared `resolveCallableOrigin`) caught the byte-identical shape. A cut sweep would
> have scored the private reader's arms "unenforced" and never found the ESCAPE. **How to apply:** before
> cutting, list the family's members by which shared `lib/` reader they call; any member that calls none
> is an A/B candidate, and the control is its sibling.

**2.** `- [a conversion can MOVE a guarantee](guarantee-moves-into-the-runtime.md) — a roster claim the
module no longer implements may have moved into a runtime predicate; plant the break before calling it a
lie.`

> `brand-in-name-position`'s roster claims a blindness tripwire; the module contains no such check.
> Neutering the derivation makes ALL 11 rows fail with `policy receipt refused: population … resolved zero
> members` — the guarantee moved into `receiptFailures`' `count === 0` (`lib/policy-pass.ts:640`) and is
> now implicitly pinned by every row, which is strictly better than the bespoke check. **How to apply:** a
> "the header claims X and the code does not do X" finding owes a planted break FIRST. The #1966 receipt
> arm and the `count === 0` predicate carry several ex-bespoke guarantees across the corpus.

**3.** `- [satisfies does not make an arm unfalsifiable](conformance-ignores-ts-diagnostics.md) — the proof
runtime does not gate on TS errors, so a "compile-time-impossible" fixture still runs.`

> `bus-belt-total`'s FOREIGN arm looks unfalsifiable: a belt member outside the union is a `satisfies`
> error. But `runVirtualExample` never asserts zero diagnostics, so the fixture runs, the arm fires, and
> the cell is UNENFORCED rather than UNFALSIFIABLE (F6, both directions). **How to apply:** never classify
> a cell UNFALSIFIABLE on a type-level argument alone — build the fixture and see.
