## PROPOSED LESSONS

Index line:

- [family-test pin substrate](family-test-pin-needs-a-same-substrate-control.md) — a disk-planted refusal pin whose green twin is an OVERLAY pin proves less than it looks

Body:

> A `runPolicyPass` refusal pin that plants its tree on DISK needs its green control planted the same way.
> The overlay-based "complete population" pin sitting above it in the file is not that control: with an
> empty overlay the ts-morph Project holds no source files, so a perfectly healthy planted tree does not
> reach a verdict at all — it tool-errors `Invalid population resolution: candidate corpus is empty`.
> The refusal pin still passes, because its `messageIncludes` names the resource status and the corpus
> error is different text, so the file reads as a two-sided proof it never had. The mixed form works and
> is two lines: plant the TREE on disk and hand the SOURCE through the overlay — the healthy arm then
> returns `toolErrors: []` and owner `success`.
> **Why:** measured 2026-09-13 on `mirror-index-family.test.ts:208`; the two symlink arms landed in the
> same commit DID carry their planted control (`:148`) and the `empty` arm did not, so the gap is invisible
> from a green suite.
> **How to apply:** when a family test grows a pin that calls `plant(...)` instead of passing an overlay,
> require a green twin in the SAME substrate in the same commit.

Second index line:

- [enforcer call-shape drift](enforcer-fixture-signature-must-match-the-real-api.md) — a gate whose fixtures `declare` a helper can pin a signature the production helper does not have

Body:

> `policy-refusal-coverage` recognises its family-test half as `runPolicyPass(<imported policy>, …)` — the
> policy as the FIRST POSITIONAL argument. The production dispatcher is `runPolicyPass(input: PolicyPassInput)`,
> one options object, and every real family test in the corpus calls it that way, so the recogniser credits
> ZERO real pins. It stays green because its own fixtures `declare function runPolicyPass(policy: unknown,
> files: unknown)` — the guide §4.8b class one level over: not a package door resolving differently, but a
> DECLARED signature that never existed.
> **Why:** guide §4.1 permits `declare`-ing the dispatcher in a fixture precisely so proofs can falsify the
> rule; the cost is that nothing ties the declared shape to the real one.
> **How to apply:** any gate whose subject is a CALL to one of our own helpers owes one real-corpus row (or
> a signature assertion) proving the shape it matches is the shape the helper actually exports.
