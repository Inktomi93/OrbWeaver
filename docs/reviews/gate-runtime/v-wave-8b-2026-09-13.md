## 5. PROPOSED LESSONS

The orchestrator owns the memory store; these are offered in its shape, one index line plus a body.

**1.** `- [policy control needs the arm's own receiver shape](e4-control-needs-a-registered-module-and-a-bare-receiver.md) — a planted control that produces 0 is usually mis-constructed, not a dead arm`

> A planted positive control for a gate arm fails silently three ways before it fails once honestly, and each
> failure looks exactly like "the arm is dead". Measured 2026-09-13 against `policy-soundness` ARM E4: control 1
> (a plain exported function with an unwrapped `ctx.resources.<door>()`) produced 0 because the arm judges only
> modules carrying a FINAL REGISTRATION; control 2 (`defineGate` added) produced 0 because the descriptor was
> type-invalid and `mustFlag`/`mustPass` are both required; control 3 (`(ctx as X).resources.trackedFiles()`)
> produced 0 because the receiver test is `bindsParameter` on a BARE IDENTIFIER and a cast is not one. Control 4
> — the exact authored shape — reddened at once. **Read the arm's collection predicate before writing the
> control, and never report a zero from a control you have not seen fire in some form.** The general rule: a
> control must reproduce the arm's SUBJECT SHAPE, not merely its subject's meaning.

**2.** `- [a recognizer's fixture can invent the API it recognizes](proof-fixture-invents-the-production-signature.md) — a declared stub with a different arity makes a dead recognizer green`

> §4.8b's rule is that a virtual project resolves a package door differently than the tree. The sibling failure
> is worse and is not in the guide: a proof fixture may `declare` the very function the policy recognizes, with a
> signature the production module does not have, and then the recognizer's `mustPass` row passes on a shape no
> real call site can produce. Worked case 2026-09-13: `policy-refusal-coverage`'s `PIN_TEST` declares
> `runPolicyPass(policy: unknown, files: unknown)`; the real dispatcher takes ONE options object, and its
> recognizer keys on `isIdentifier(getArguments()[0])`, so the family-test half of a live gate could never fire
> and its `fix` promised an unreachable route. **When a policy recognizes a CALL to a project function, one row
> must drive it against the real call shape** — or, cheaper and decisive: plant the fixture-shaped call on the
> real tree and check the finding count moves. If it moves for the fixture shape and not for the corpus's shape,
> the recognizer is fitted to its own stub.

**3.** `- [run the differential the conversion did not](verifier-runs-the-owed-4-6-differential.md) — a frozen descriptor as a scratch sibling costs one command`

> Three conversions in this wave (`aecbc6c6c`, `97e68be91`, `630cfe24c`) landed §4.6-silent. Running the
> differential yourself is cheap and turns "unrecorded" into "recorded and clean": `git show <sha>^:<gate path> >
> tooling/src/verify/gates/<lane-prefix>-legacy-<name>.ts` (a SIBLING in the same directory, so its relative
> imports resolve — the guide's own `?query`-cache rule), then `runPass([descriptor], projectCtx(root))` and
> compare against the final policy driven through `runPolicyPass` over the SAME project. It found the two
> genuinely useful facts in this wave: that `test-layout`'s 53 real-tree findings are legacy debt carried
> unchanged rather than a conversion regression, and that `test-presence`'s widening removed exactly the two
> subjects its header claimed and nothing else. Delete the sibling in the same turn.

**4.** `- [a "deferred behind another lane" item ages into a false header](deferral-outlives-its-blocker-and-the-header-lies.md) — re-derive the blocker, then re-derive the claim it left behind`

> `#2155` item 2 was deferred behind a merge that owns `contract/policy-pass.ts`. That merge landed; the item did
> not; and the landed contract's own header now asserts that `lib/policy-pass-context.ts` composes from its
> constants when that file has **zero** references to them. Same family as read-first §0.3 ("nothing re-opens a
> refusal when its blocker lands"), one layer over: **a deferral leaves a claim behind in the file the OTHER lane
> wrote.** When you find a deferral, grep the blocking module's header for a list of consumers and check each
> one, not just whether the blocker landed.
