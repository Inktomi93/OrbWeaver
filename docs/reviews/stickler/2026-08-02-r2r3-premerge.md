### F2 — MEDIUM · SCENE OPENS leaks raw ref keys for roster actors into the model prompt
- `packages/server/src/domain/rpg/substrate/delta.ts:493-511` — `buildFirstSnapshotBlock` resolves a
  presence key's display name via `actorState.find(...)?.identity?.name ?? key`. A ROSTER actor's
  row carries NO identity (by R2 design), so the fallback prints the raw key.
- **Failure scenario:** turn 1 of a fresh game — `establishScene` FORCES a non-empty `presentUpsert`
  on an empty cast, and the model typically lists the roster character in the scene. The applier
  resolves her to `character:<id>`, and `applyPresencePatch` mints her identity-less `actorState`
  row. On the NEXT gather (`prev === null` — the lineage's first snapshot) the reminder renders
  `SCENE OPENS: The Ford · with character:chr_01k…` (or `user:usr_…` for the player). A branded
  TypeID in the prompt is exactly the projection-clean class the contracts ban ("an id is never
  model-facing" — the suite's own exemption cites), and it invites the model to echo ids as names.
  One-gather blast radius per lineage (later gathers use the per-plane renderers, which resolve
  names correctly via `ctx.rosterNames`/`actorLabel`), but it fires on effectively EVERY new game.
- **Evidence:** code trace this session (delta.ts:500 `nameOf`, apply.ts:306-325 presence mint,
  compose/rpg.ts:415-428 establish-when-unset); pre-R2 comparison
  `git show 6e43af99:…/delta.ts` → the old block printed `c.name` (a human name for every presence
  row, roster included) — this is a regression the branch introduced, not pre-existing.
- **Why no test caught it:** the reachability suite's SCENE-OPENS arm has no roster-carrier probe —
  `openingBeat`/`withStage` only stage CAST carriers, so the first-snapshot block was never read
  with a roster member present. Add that probe with the fix.
- **Fix:** thread the `DeltaContext` (already at the call site, `buildDeltaBlock`) into
  `buildFirstSnapshotBlock` and resolve roster keys through `ctx.rosterNames` (the `actorLabel`
  rule), falling back to `identity?.name` for cast.

### F4 — LOW · the raw non-slug castKey hand-mint hole — RULED: close it at the CONTRACT (the lane's seam call is the wrong side)
- The lane flagged it honestly: `rpgActorRefSchema`'s cast arm is `castKey: z.string().min(1)`, so a
  raw API caller can `patchActor`/`dismissActor` with `castKey: "Sister Vesna"` and mint a sibling
  row (`cast:Sister Vesna`) beside the model's `cast:sister-vesna`. The sibling is unreachable by
  every model write (the appliers resolve names through `rpgCastSlug`/display-name), renders as a
  duplicate person in the panel, and only `dismissActor` with the same raw key removes it. The lane
  declined verb-boundary normalization "to keep `actorRefKey` a pure projection".
- **Verdict (asked for, given):** the house pattern is PREVENT-AT-SCHEMA (the R6 enum-constraint
  precedent; the stamped-id write-boundary-gate precedent) — and it costs `actorRefKey`'s purity
  nothing: a `.refine((k) => k === rpgCastSlug(k))` on the cast arm (or normalization inside the two
  verbs) makes the non-canonical key UNREPRESENTABLE at the wire while `actorRefKey` stays a pure
  projection over already-canonical data. Pre-launch there is no stored non-canonical key to strand
  (NO-LEGACY + wipe), and a later-stored one failing parse-on-read loudly is the corruption posture
  working. Severity LOW because the hole is host-gated, own-game-only, and unreachable from the
  shipped client (every client ref echoes a server-projected row; the seed uses canonical slugs) —
  route it as a fix, not a blocker.
- **Evidence:** contracts/rpg/actor.ts:35 (the bare `min(1)`), verbs/patch-actor.ts:41-53 +
  dismiss-actor.ts:34-49 (no normalization), apply.ts:73-96 (the model path always slugs), client
  call-site reads (scene-cast/status/inventory all pass `actor.actorRef` from the view).
