## Findings

### \[P1] Mobile: the "Blank chat" button is clipped outside the dialog — NEW, introduced by the #334 footer

**What.** At the real mobile mount the action footer is a `nowrap` flex row with `justify: end`, and
its two buttons are wider than the dialog's content box. The overflow goes LEFT, so `Blank chat`
paints outside the dialog and is cut off by the popup's clip.

**Measured** (`--mobile`, 430×932, dialog `x=32 → right=398`, w=366; footer content box w=316):

| selection | button | `x` | width | outside dialog? |
| - | - | - | - | - |
| 1 selected | `Blank chat` | **5** | 120 | **yes — 27px clipped** |
| 1 selected | `Start chat with 1 character` | 130 | 231 | no |
| 3 selected | `Blank chat` | **−3** | 120 | **yes — 35px clipped** |
| 3 selected | `Start chat with 3 characters` | 123 | 238 | no |

Desktop is fine (dialog 560px; `Blank chat` at `x=519`, no clip) — this is a **width-range defect**,
not a point defect, and it gets WORSE as the Start label grows with the selection count.

**Why it hurts.** "Blank chat" is the second of two exits from this modal and the only path to a
characterless room. On a phone it reads as `nk chat` with its `+` icon gone — a mangled, half-visible
control. A first-timer reads it as a rendering bug, not an option.

**Fix.** `adapt: the new-chat action footer — `Row`at`new-chat-picker-surface.tsx:118`.` Let the
footer wrap (`flex-wrap` / `Row` wrap token) or make the two buttons share the width at narrow
containers (`flex-1` + `min-w-0` with a truncating label), and shorten the Start label at narrow
widths (`Start (3)`), driven by `@container` per the §0 container rule — not a viewport media query.
Receipt to close it: the same geometry eval showing `clippedLeft: false` for `Blank chat` at 1 and 3
selections on `--mobile`.

**Receipt.** `reports/snaps/vv-334-mobile-3sel.png`, `vv-334-mobile.png`; geometry eval above.

**Instrument honesty — this class is invisible to two of our detectors:**
`snap --expect-no-overflow '[role=dialog]'` **PASSED (`overflow=0x0`) on the exact frame where a child
was 35px outside the dialog's left edge** — `justify-end` overflow is negative and `scrollWidth`
cannot see it. `pnpm design-audit / --goto modal:newChat --mobile` also did not fire
`clipped-positioned-child`. The screenshot + per-button rect table is the only instrument that saw it.

### \[P1] Keyboard: opening "New chat" lands focus on a dead wrapper — PRE-EXISTING, not a #334 regression

**What.** `useFocusOnMount(surfaceRef)` puts focus on the picker's outer `<Stack ref tabIndex={-1}
className="outline-none">` (`new-chat-picker-surface.tsx:46-47,90`). That element is not the search
box and is not inside cmdk's key handler, so **every keystroke a keyboard user makes on arrival is
swallowed.**

Measured, three arms:

| arm | result |
| - | - |
| at mount | `activeElement = DIV.relative`, `tabIndex −1`, `boxShadow: none`, `outline: 1px none` — **no visible focus indicator at all** |
| at mount, press `a` then `b` | `cmdk-input.value === ""` — the letters go nowhere |
| at mount, `ArrowDown` + `Enter` | nothing selected; Start still `"Pick a character to start"`, `disabled: true` |
| **after one `Tab`**, `ArrowDown` + `Enter` | works — Start becomes `"Start chat with 1 character"`, `disabled: false` |

Tab cycle from there: `Search characters…` → `Blank chat` → `Close` → (wrap) `Search characters…`,
`:focus-visible = true` at every stop, ring `oklch(0.158 0.006 60)` on the buttons. The trap itself is
correct; only the entry point is wrong.

**Why it hurts.** Sam opens the modal, types the character's name, and nothing happens — with no focus
ring on screen to explain why. This is the difference between "searchable" and "operable".

**Verified pre-existing:** `git show 875c7b4b0^:…/new-chat-picker-surface.tsx` already has
`useFocusOnMount(surfaceRef)` at :39 and `tabIndex={-1}` at :82. The #334 fix neither caused nor
addressed it. It matters now because #334's own done-bar is "selecting a character gives an obvious,
in-view way to begin" — which is true by pointer and false by keyboard.

**Fix.** `clarify: the picker's initial focus.` Either pass `autoFocusSearch` through from
`NewChatPicker` (the prop already exists, `character-picker.tsx:109`, and the "the two would fight
over the caret" comment no longer applies once the surface stops claiming focus), or drop
`useFocusOnMount` and let Base UI's dialog initial-focus land on the input. Receipt to close it:
`snap / --goto modal:newChat --key a --eval '<read cmdk-input.value>'` returning `"a"`.

### \[P2] The teaching label on the disabled Start button reads at 2.64:1

`pnpm design-audit / --goto modal:newChat` fires one P1:
`contrast … 2.64:1 (need 4.5:1) · dimmed α0.50` on
`[data-slot=dialog-popup] … > button.inline-flex[data-slot=button]:nth-of-type(2)`. Confirmed that is
the disabled Start: `{label:"Pick a character to start", disabled:true, opacity:"0.5"}`.

**Triage — this is NOT a WCAG failure** (disabled controls are exempt from 1.4.3), so I am demoting
design-audit's P1 to **P2**. But it *is* a real defect against the fix's own stated intent: the header
says Start "stays rendered but DISABLED at zero selection (**teaching** 'Pick a character to
start')". A teaching label at 2.64:1, sitting inside the loudest orange fill in the modal, is the
worst of both — it grabs the eye as the primary CTA and then can't be read.

**Fix.** `quieter: the zero-selection Start button.` At zero selection, render it as a low-emphasis
(ghost/outline) control carrying the teaching copy at full opacity, and reserve the primary orange
fill for the state where it actually does something. Receipt: `design-audit --goto modal:newChat` with
no contrast finding, plus the screenshot showing one focal control.

**Instrument disagreement, published:** `snap --contrast '[role=dialog] button:last-of-type'` reports
**7.56:1 PASS** on the same element (`ui-component · need 3.0 · css-resolve`) because the css-resolve
path does not composite the element's own `opacity: 0.5`. design-audit's 2.64:1 is what the eye reads;
snap's 7.56 is the authored color. Trust design-audit here.

### \[P2] World-info Rename now lives in two homes — NEW, same class as #271, different verb

\#271 converged **Delete**. Driving the surfaces surfaced that **Rename** has the exact defect #271
existed to kill, on world-info only:

| home | receipt |
| - | - |
| row kebab | `menu "Actions for New book": menuitem "Rename" · "Duplicate" · "Export" · "Delete"` |
| editor dialog | `dialog "Book details": textbox "Name" · textbox "Description" · Cancel · Save`, reached from `button "Edit book details"` |

Tags and regex both rename in the editor's `Name` field ONLY — no kebab Rename. So the same verb has
one home on two collections and two homes on the third.

**Fix.** `distill: the world-info row kebab.` Drop `Rename` from the WI kebab (the Book details dialog
already owns naming, and it owns Description alongside it — a rename-only second door is the narrower,
worse one), or file the fork explicitly if the owner wants row-rename everywhere. Receipt: the WI
kebab aria reading `Duplicate · Export · Delete`, matching regex.

### \[P3] Two untitled regex scripts produce two identically-named kebabs

Creating a script defaults its name to "New script"; two of them give the list two rows named
`"New script"` and two buttons named `"Actions for New script"`. A screen-reader user cannot tell
which is which from the accessible name (the disambiguating text — `no pattern yet · edited 3m ago` —
lives inside the row button, not the kebab's label). Low priority: real libraries have named scripts.
**Fix.** `clarify:` include the row's distinguishing datum in the kebab label, or give a new script an
ordinal default (`New script 2`). Receipt: `--aria '[aria-label="Configuration list"]'` with two
distinct kebab names.

## ARIA-navigability recommendations

1. **`new-chat-picker-surface.tsx:90`** — the `<Stack tabIndex={-1} className="outline-none">` takes
   initial focus and swallows keystrokes. Remove `useFocusOnMount(surfaceRef)` + `tabIndex={-1}` and
   pass `autoFocusSearch` to `CharacterPicker`, so focus lands on `combobox "Choose characters"`.
   (P1 above.)
2. **`new-chat-picker-surface.tsx:118`** — nothing announces the selection COUNT changing. The Start
   button's accessible name carries it (`Start chat with 3 characters`) but a user whose focus is in
   the search box never hears it. Add `role="status"` copy, or `aria-live="polite"` on the count, so a
   toggle announces "3 characters selected".
3. **World-info row kebab** — drop `Rename` (P2 above); the same verb reachable under two different
   accessible names ("Rename" in a menu vs "Edit book details" → "Name") is exactly the recall burden
   §13's single-homing rule exists to prevent.
4. **`Actions for New script`** ×2 — give the kebab a disambiguating accessible name (P3 above).

Everything else in both surfaces passed: dialog/banner/heading structure, `combobox`+`listbox`+
`option` with `[selected]` on picks, `role=menu`/`menuitem`, `alertdialog` with heading+description,
`list`/`listitem` on the collection rows, and `:focus-visible = true` at every Tab stop I walked.

**RETRACTIONS.** Two concerns I formed and then killed with receipts:

- *"The opacity-0 kebab is a stray-click hazard at the row's right edge."* **Wrong** —
  `pointer-events: none` at rest; `elementFromPoint` at the kebab's centre returns the row's own
  `SPAN`, not the button.
- *"The config list has two unlabelled filter textboxes"* (they showed as `textbox ""` `[dom]`
  fallbacks in `--map --include-hidden`). **Wrong** — those are the large-group filter inputs, inert
  and out of the a11y tree below the windowing cap. The live `--aria '[aria-label="Configuration
  list"]'` with a group expanded contains no unlabelled control.

## Taste & flow verdict

**The new-chat picker looks good.** Genuinely. Dark popover, one clear heading, one search field, a
clean row rhythm of avatar + name, a check mark on picks, and a bordered footer holding exactly two
verbs. The eye lands on the search box, the work is obvious, and the exit is where you'd reach for it.
The 5-second test passes cold: anyone would name this "pick who's in the chat". The footer is the
right call — the old shape (Start as row 1 of the list) was the kind of thing that reads fine in code
and is baffling on screen.

Two things a person would notice:

- **The disabled primary is the loudest thing in the modal and does nothing.** Before you pick anyone,
  the eye goes straight to the orange fill, tries it, and gets nothing — and the label explaining why
  is the least legible text on the surface (2.64:1). One focal element per region (CD3) is being spent
  on a control that is inert. It should be quiet until it's live.
- **The Start button's width breathes with the selection count** (212 → 231 → 238px), which shifts
  `Blank chat` leftward on every toggle. On desktop it's a twitch; on mobile it's what pushes `Blank
  chat` off the edge. Fix the button's width or its label and both problems go.

**The config list looks fine and flows right.** Three collapsible library groups with caps kickers,
scan-line rows (swatch · name · usage), floating kebabs that stay out of the scan column — this is the
LIST region doing its job (§14). Finding happens here, editing happens in CONTENT. The one oddity my
eye caught: the tag usage column renders as `1` (bright) then a wide gap then `use` (muted), so at a
glance the count and its unit read as two separate columns rather than one datum. Cosmetic; not filing
it.

**IA / single-homing (§13):** Delete is now genuinely single-homed across all three collections — that
is the whole point of #271 and it landed. The one remaining two-homes concept in this area is
world-info **Rename** (P2). No duplicated affordances found in the picker.

## What's genuinely working (don't touch)

1. **The Start footer's structural position.** It is a sibling of the listbox, not a `forceMount`ed
   `CommandItem` — which is why the ARIA tree now reads as a dialog with two buttons instead of a list
   containing a fake character. Do not move it back inside `CommandList` for any layout reason.
2. **The D123 dismiss boundary.** Escape closes, mints nothing, and the console proves it — one
   `chat.startChat` in a run containing two full select-and-leave cycles. That's a hard property held
   under a real drive, not an assertion.
3. **The three delete confirms carry their own real blast radius.** "removes the tag from 5
   characters" vs "removes the book and every entry in it, and detaches it everywhere" — same shell,
   different truth per collection. This is the pattern; keep it when the fourth collection arrives.

## The single biggest opportunity

**Make the picker's footer honest at its narrowest real mount.** One `@container`-driven wrap (or a
count-abbreviated Start label) fixes the P1 clip, kills the width-jitter on every toggle, and removes
the pressure that a growing label puts on the layout — three symptoms, one move. Pair it with quieting
the zero-selection Start and this modal is done.

### Probe-usage note

Zero chrome-devtools MCP calls. Everything above is `pnpm snap` / `pnpm design-audit` Bash calls. Two
snap footguns paid for here and worth carrying: **`--idle` deadlocks on this app** (the SSE stream
never lets the network go quiet — `NAV ERROR nav/wait threw: page.goto: Timeout 15000ms`), and
`--wait-for` takes a SELECTOR (truth-repair, #550: this line originally said "takes TEXT"), so a bare
`--wait-for 'Delete'` waits on a `locator('Delete')` CSS tag that never exists — rendered text needs
`--wait-for 'text=Delete'`; snap now refuses the bare-prose form with exit 3.
