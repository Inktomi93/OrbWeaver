# a plugin is USER-SCOPED: anyone installs one FOR THEMSELVES, it runs under them, and OWNERSHIP OF THE ROW is the entire authority model — there is no role gate on any management verb and deliberately no admin any-row branch

## Context

Not recorded in the ledger row.

## Decision

Owner-ruled 2026-08-24: *"plugins are user scoped and should be installable by anyone — it runs under them for their session; just like SillyTavern extensions you can install for yourself or the whole server, so the latter is admin gated."* The v1 shipping shape gated `install`/`upgrade`/`setGrant`/`setEnabled`/`uninstall` on `can(caller,"admin",{kind:"global"})`; that gate is REMOVED. **Four clauses.** (a) **THE OWNER-SCOPED ROW LOAD IS THE GATE, and it is the only one.** `plugins.ownerId` is stamped at install from `caller.userId`; every management verb reaches its row through `getById(db, caller.userId, pluginId)` (`domain/plugin/persistence/plugins.ts`) and a foreign or absent id is the SAME leak-free `PluginNotFoundError`. `list` takes no id at all and filters `WHERE owner_id = caller.userId`. `domain/plugin`'s `PluginContext` therefore carries NO `can` seam — the privilege kernel has no question to answer here, and a seam nothing asks is a seam that gets answered wrong. (b) **AN ADMIN MAY NOT MANAGE ANOTHER USER'S ROW, and the reason is a confused deputy, not tidiness.** `setEnabled` RUNS the plugin's untrusted guest bundle as the CALLER: activation builds the membrane bridge over `caller.userId` and hands `caller` to the PL-C ceiling as the installer (`domain/plugin/activation/activate.ts`), so the guest's `worldinfo.write`, `global_vars`, `notify`, `llm.quiet` spend and room reach all resolve against whoever pressed the switch. A cross-owner enable would therefore execute one user's code under another's identity and credential — the escalation is IN the act, so no role is senior enough to perform it. The apex `owner` role is refused on a foreign row exactly like a plain user. (c) **A NEW EXPOSURE IS PRICED AT THE INSTALLER'S OWN CEILING, so opening install to everyone grants nobody anything they did not already have.** A plugin can reach only what its installer can reach; the per-plugin belts are already keyed by `plugins.id`, which is unique per `(ownerId, slug)` and therefore per-user by construction (the hourly egress + `llm.quiet` floors, the notify cooldown's `(plugin, chat)` key, the crash counter and its owner notification, the `plugin_kv` `(plugin_id, owner_id)` belt) — none of them assumed a single global installer, and no ceiling was added or moved by this ruling (spend policing is not a system belt). The one per-USER belt, `runSnippet`'s concurrency gate, was already keyed that way because a snippet has no row to key. (d) **THE SERVER-WIDE INSTALL IS AN ADMIN-TRIGGERED FAN-OUT OF PER-USER ROWS — there is no shared install, and that is what makes it possible at all.** An admin PUBLISHES a bundle (`plugin.installForAllUsers`, recorded once in `admin_distributed_plugins`, keyed by slug) and the server then runs the ORDINARY per-user install for every user under THEIR OWN Principal: each gets their own `plugins` row, disabled, zero grants, `pending_reconsent` raised — the example-seeder's consent-first posture, generalized to arbitrary bundles at runtime. A user who already holds that slug at ANY version is SKIPPED and reported; their row is theirs. `plugin.uninstallForAllUsers` is the same fan-out in reverse and SKIPS a recipient whose row has diverged from the distributed version (slug **and version** must match — an admin withdrawal may not delete a plugin somebody upgraded themselves). New users get the published set on their first authed request through the self-scoped `plugin.applyDistributedPlugins`, latched per user in `UserSettings.onboarding.distributedPluginsApplied` (the `ensureSeeded` precedent — the latch is also the deletion-respect guard). **The two open questions this clause used to record are DISSOLVED rather than answered:** there is no shared row, so no consent junction is needed; there is no shared principal, so "whose principal does it run as" never arises — every copy runs as its own owner. **What it deliberately CANNOT do is force-enable.** Enabling runs the guest bundle as the enabler (clause (b)), so the fan-out only ever MINTS rows that can do nothing; per-user enable stays the consent act and no admin verb can perform it. The admin gate is `requireAdmin` injected as a SEPARATE `PluginDistributionDeps` bundle, never in `PluginContext` — clause (a)'s "no `can` seam on the per-row verbs" stands unchanged, because the distribution question is global ("may this caller publish to the deployment") and has no per-row answer. HOMES: `domain/plugin/verbs/{install,uninstall,apply}-*.ts` + `substrate/distribution.ts` (the one per-recipient landing) + `persistence/distributed-plugins.ts`; the record's `bundle_asset_id` FK is CASCADE (assets are per-user, D21 — RESTRICT would pin the publishing admin's account open) and is registered in `ASSET_REFS` so the published bytes are never reaped under a live distribution. The client half is a viewer-gated settings-SECTION at the `plugins` anchor (`features/plugin/lib/plugin-distribute-section.tsx`), never a gate on the pane. ENFORCEMENT, tiered honestly: clause (a) is behavioural — the cross-tenant IDOR sweep probes `upgrade`/`setGrant`/`setEnabled`/`uninstall`/`getLog` as a stranger holding the owner's real `pluginId` and requires leak-free NOT_FOUND plus an untouched row (`tests/server/transport/cross-tenant-sweep.suite.int.test.ts`), and each verb carries its own cross-user refusal pin including an apex-role arm (`tests/server/domain/plugin/verbs/*.int.test.ts`); the belt was proven by BREAKING it (removing the owner predicate from `getById` reds exactly those pins and makes a stranger's `setEnabled` resolve). Clause (b) has no gate and cannot get one — a future `getByIdAny` would satisfy every structural check — so it is REVIEW-tier, stated in the persistence header and the `PluginContext` comment as the thing a reader must not re-add. Clause (d) is behavioural too: the admin gate, the consent posture landed per recipient, the already-installed skip and the version-divergence skip each carry a pin (`tests/server/domain/plugin/verbs/{install,uninstall,apply,list}-*-users.int.test.ts` / `list-distributed-plugins.int.test.ts`), the record's PK/CASCADE semantics are pinned at `tests/server/domain/plugin/persistence/distributed-plugins.int.test.ts`, and the three admin procedures are classified EXEMPT-with-reason in the cross-tenant sweep. The client half moves with the server half: the Plugins settings pane carries NO viewer gate (`packages/client/src/features/plugin/lib/plugins-group.tsx`) while the Distribute SECTION carries `when: viewer.isAdmin`, both pinned by `tests/client/features/config/surfaces/config-content-surface.ct.tsx`.
