# THERE IS ONE GAME MODE; THE RULESET IS A SETTING AND ITS SWITCH IS ADDITIVE; AND A USER-INITIATED START/STOP REVEALS ITS OWN RESULT (amends `Context-Panel-Program.md` §4.1 — the ruling survives, its INPUT changed)

## Context

Not recorded in the ledger row.

## Decision

Owner-ruled 2026-08-30 (#862 + #863), verbatim on the switch: *"a Ruleset switch on a LIVE game is ADDITIVE — apply the new ruleset's vocabulary (attributes, pools, trackers) beside what already exists; switching back hides nothing; no data loss, no confirmation dialog."* **Four clauses.** (a) **ONE START ACTION PER DOOR.** Both front doors (the ⋯ menu item, the Game meta-tab door) minted the identical `lite` game and differed only by which packaged profile they passed, so the "choice" was a setting wearing a door's clothes — and `full` stays unmintable (`RpgModeUnbuiltError`). A game is now STARTED directly and born `freeform`; the retired `createGame.profile` wire arm is REPLACED (pre-launch NO-LEGACY) by an optional `ruleset`, and the seeder/`startAsGame`/`planGameBirth` chain carries the same axis. (b) **`ruleset` IS A HOST SETTING ON THE GAME TAB, and it is a SELECTION, never a second storage for the vocabulary** — `config.statProfile` + `config.trackers` remain the truth; the setting records which packaged vocabulary was applied. Home: `contracts/rpg/ruleset.ts` (the axis + `RPG_RULESET_PROFILE`/`RPG_RULESET_DICE` + the pure `applyRulesetVocabulary` merge); the write door (`domain/rpg/verbs/game/update-config.ts`) decides only WHEN the merge runs. (c) **THE APPLY IS ADDITIVE AND CHANGE-GATED.** Attributes and seeded trackers are appended BY KEY (an existing key keeps the game's own label — a host rename survives a re-apply); `skillGoverning` unions with the game winning a clash; the profile scalars (`range`/`modifier`/`defaultAttribute`/`perceptionAttribute`) are adopted ONLY where the game has none, because a freeform game's placeholders would leave a d20 vocabulary un-rollable. `freeform` carries no vocabulary, so switching back is a NO-OP by construction — which is exactly the owner's "switching back hides nothing". The merge runs only on a CHANGED value: re-sending the current arm (an unrelated config write, the autosave form) must never resurrect an attribute or tracker the host deleted, which is also why the control is a path-scoped `updateConfig({patch:{ruleset}})` and NOT a field of the scalar autosave form. **A dead setting is a defect, not a deferral:** the dice-ask row above the composer publishes `RPG_RULESET_DICE[ruleset]` off `getGame.publicConfig` — `freeform` publishes NONE and the band collapses — so the setting has a visible consequence for every member, not only the host who flipped it. (d) **A USER-INITIATED START/STOP IS AN EVENT AND IS OWED H1 FEEDBACK; ARRIVAL IS NOT.** `Context-Panel-Program.md` §4.1's "no ceremony, a game is content, not an event" is CORRECT and its MECHANISM is untouched — no takeover animation, ever, in either direction, and arrival at a game room still swaps like any chat switch. Its INPUT changed: the sentence also named `createGame`, and a mutation the user just performed is not arrival. Measured cold on 2026-08-30 with the context panel CLOSED (the shipped default), a toggle changed exactly one thing on screen — four dice chips — while the polite live region still read the stale "Loaded chat." four seconds later in BOTH directions, and the post-start landing was whatever `contextTab` happened to hold (worst case an empty host-console schema form). So a user-initiated transition (the ⋯ item or a door button — never a chat switch, never a remote update) additionally fires ONE `role="status"` announcement and, on START, opens the CONTEXT panel on `rpg.status` from BOTH doors. Neither is ceremony; neither costs a frame. **Riders, same ruling:** the kept-state reassurance moves from a native `title` (dwell-gated on a pointer, ABSENT on touch, only a description to a screen reader) onto the item as a visible second line wired as its accessible description, in its own separator group, with the door's pending admission — and NO confirm dialog, because the action is genuinely reversible. Both mutations invalidate `chat.listChats` as well as `chat.getChat` (a mutation's invalidation set is a UX surface: the list's ⚔ marker is the same fact from a different read, and it outlived the toggle for a whole session). The chat-list row keeps a QUIET `Game chat — paused` marker for a game that exists but is off, derived from the same opaque pointer as `isGame` (`ChatSummary.gamePaused` — chat stays rpg-table-blind; `isGame` is NOT widened, and a disengaged game still claims no panel). HOMES: `contracts/rpg/ruleset.ts` · `client/src/state/game-mode-transition.ts` (the one home for the noun — `game mode`, everywhere — and for what a transition announces/reveals, because the two doors live in different client features and may not import each other) · `client/src/state/status-announcement-store.ts` (the imperative live-region channel `app-root` renders through its ONE announcer). PINS, red-first at HEAD (8 CT failures, all green after): the one-start-action + announcement + landing + accessible-description + list-census pins in `tests/client/features/chat/components/chat-options-menu.ct.tsx`, the single-door admission in `tests/client/features/rpg/components/rpg-game-door.ct.tsx`, the freeform-no-dice arm in `tests/client/features/rpg/lib/dice-ask-source.ct.tsx`, the paused marker in `tests/client/features/chat/surfaces/chat-list-surface.ct.tsx`; the additive law itself in `tests/contracts/rpg/ruleset.contract.test.ts` (the d20 → freeform → d20 round trip) and at the write door in `tests/server/domain/rpg/verbs/game/update-config.int.test.ts`; the server `gamePaused` derivation in `tests/server/domain/chat/verbs/read.int.test.ts`.
