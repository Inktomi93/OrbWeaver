  - **The identity-resolution invariant (headline).** `infra/auth` must NEVER yield a `userId`/`role`; every mode's identity→row resolution is a DOMAIN step the `entry/auth/seam` invokes; the `Principal` is constructed ONCE per request at the seam, immutable thereafter; authorization (`can()`/membership) runs PER-CALL on that Principal (a different cadence — never cached onto the Principal). Three of four modes already obey this; the cookie path (`local`/`oidc`) deviated: `ResolveDeps.validateCookie` is typed `=> ResolvedIdentity` (no `userId`), so wiring it to `sessions.validate` (which sessions.md §"resolved twice" mandates return `userId`) forces the seam to RE-QUERY (violates resolve-once, D-§38) or double-validate — recreating the neo "validate threw the id away" bug at the type boundary. **Resolution (Route A — = what sessions.md already prescribes; confirmed against ASP.NET/Spring/Passport prior art, this is Spring's verify→`UserDetailsService`→construct split):** the cookie→user read is DOMAIN resolution (`sessions.validate` returns identity+`userId`), called directly by the seam; `infra/auth` owns only the db-free verification paths (single-user, forward-header verify, the origin-gated owner fallback). `validateCookie` is REMOVED from `ResolveDeps` + the `infra.md` "`validateSessionCookie (= sessions.validate)`" equation dropped, when 4c/4e land (FLAG planted at the port now). Why infra is right to refuse the id: forward-header ALREADY does this (verify in infra → `provisionIdentity` resolves in domain → seam constructs); the cookie is the only mechanism whose verification step IS a user-row read = resolution, not verification. Generalizes: the agent-principal mint (D-§96) is a SECOND construction context (a turn, not a request) inheriting the same construct-once/carry-immutable discipline.
