## The one-paragraph design

`domain/imagery` is a server-side **orchestration leaf** (8-slot template, Phase 7 additive graft)
that turns chat/character context into a generated image and hands back D44 render blocks. The core
is the **two-step**: a mode-keyed prompt template runs as a **quiet shaper call** on the `summarize`
role (never posted, billed to `triggeredBy`), the reply is normalized by a pure `processReply`, and
the result feeds the hosted `generateImage` role (D39 — hosted-only, forever). Generated bytes land
in the per-user `assets` CAS as kind `"generated"`; each image gets ONE provenance row in a new
minimal `imagery_generations` table (the doc-04 §Review-flagged delta from "no DB table") which
powers the **identity-hash reuse gate** (marinara B2: pick-before-generate — a portrait for an
unchanged card is returned, not re-bought) and anchors generated assets against GC. Hosted image
**EDIT** rides an additive `ImageGenerateRequest.edit` payload gated by a new
`ModelCapability.input.imageEdit` axis (the D45 vision-gate pattern); its first consumer is
**avatar-reference conditioning** (marinara B3: `useAvatarReference` feeds the subject's avatar in
as an edit reference so art stays on-model, drop-with-warning when the model can't). Imagery never
writes to chat and owns no message: `chat.generateImage` (the D47 #1 caller), the automation Tier-1
`generate_image` action arm (D46 — this IS `/imagine`), the D48 `generate_image` tool, expressions'
sprite-sheet verb, and rpg's illustration workloads all inject `imagery.generatePicture` through
one front door. All verbs are SYNC — no imagery-owned `WorkloadKind` (doc 04 §4).

## Standing decisions a cold agent must not re-litigate (committed upstream — cite, don't reopen)

Hosted-only image generation, local SD backends permanently rejected (D39/D49) · imagery is a LEAF,
not a chat sub-feature (D49 — one-home + `domain-no-cross-feature`) · `/imagine` is a D46 Tier-1
automation action, never a bespoke command engine · the render model is the typed
`MessageContentBlock` union (D44), never ST's `extra.media` · ONE captioner — multimodal modes
reuse the D45/D47-6 vision op · the 7-member `PROMPT_TEMPLATE_MODES` tuple and the
`generatePictureRequestSchema` wire shape (`domains/imagery.md` §6.1) · the `"generated"`
`AssetKind` + the `ImageGenerateRequest` widening are born-compliant contracts-pass items
(`domains/imagery.md` §7) · sprite-sheet generation (marinara B1) is EXPRESSIONS-owned — imagery is
its injected dependency, never its home (doc 04 §5) · generated bytes are per-user single-owned
assets (D21).

## Review flags (deltas + arguments for the lead — every change to the committed doc's letter)

1. **"No DB table" is superseded — `imagery_generations` (doc 03 §4).** `domains/imagery.md`
   states three times that imagery owns no table. The B2 reuse gate needs durable
   `(assetId ↔ mode, subjectCharacterId, identityHash, prompt)` provenance, and — the load-bearing
   discovery — WITHOUT any FK reference, a generated asset's only pointer lives inside
   `message_variants` content-block JSON, which the assets GC ref-registry cannot see: the
   mark-sweep would reap live in-chat images. The provenance row is both the reuse index and the GC
   anchor. Rejected alternatives (prompt-in-asset-meta, reusing `gallery_items`) argued in doc 03
   §4.2. Consequence for `assets.md`: the asset-ref registry gains `imagery_generations.assetId`.
2. **`GeneratedPicture` goes plural (doc 01 §3.3).** The committed sketch is singular
   (`assetId + block`); resolving the committed-OPEN Q5 (`n` up to 4 → n media blocks in one
   message) forces the result to carry n images. This is a Q5 resolution, not a re-decision.
3. **`ImageEditInput` gains optional `references` (doc 01 §4).** rpg-design/08 §2 already commits
   "up to 4 reference images … into `ImageEditInput`-style references"; the committed single-image
   shape cannot carry them. Additive optional field; the game-side consumer defined the need.
4. **`extractPrompt` joins the public `ImageryService` (doc 01 §3.1).** The committed doc lists
   `verbs/extract-prompt.ts` but the interface sketch showed 2 methods. The preview-before-spend
   flow (ST's `/imagine edit:true`; rpg's `dryRun` cousin) needs extraction callable standalone.
5. **§8 open questions Q1/Q2/Q4/Q5 are resolved to their proposed defaults, Q3 is designed**
   (doc 04 §6, doc 03 §1) — the committed doc said "resolve before build"; this set is that
   resolution.
6. **Sibling-doc obligations raised:** `assets.md` — the `"generated"` kind (already D49 law), the
   ref-registry addition (item 1), and a `readAsset`-style owner-gated byte-read op imagery injects
   (doc 01 §2; whether assets grows a `readOwned` verb or compose pairs `getMetadata`+CAS is the
   assets owner's call). `chat.md` — the quiet-extract op + the `chat.generateImage` caller verb
   (doc 04 §2). Providers — `image_edit_dropped` joins `WARNING_CODES` with two real emit sites
   (doc 03 §2).
7. **Citation correction:** the external-fetch SSRF prerequisite (`safeFetch`) is documented in
   `core/Tier-3-Infra.md` (the staged `infra/network/egress.ts` seam), not gallery.md — doc 04 §7
   cites the real home.
8. **PD flag:** imagery's registry flag is **PD-93** (the D49/BUILD-PLAN `PD-54` on imagery is a
   verified copy-paste stale — `Core-SillyTavern-Feature-Map.md` §note 1).
9. **RESOLVED (design-review IMG-2, 2026-07-02) — the flagged divergence is STALE.**
   `proposed/automation-design/03-actions.md` §1.7 as it stands IMPORTS
   `generateImageActionArgsSchema` from `@orb/contracts/imagery` verbatim (and names the inline
   alternative as rejected) — exactly this set's position. The "narrower
   `{type, mode, promptTemplate, quiet}` arm" this flag described was an earlier automation draft;
   no divergence remains. One vocabulary, one schema home (doc 01 §6 / doc 04 §1).
10. **D51 persist-path wording corrected (design-review IMG-1, 2026-07-02).** Doc 04 §2.1/§2.3 now
   state the D51 law explicitly: the persisted message body is a STRING with embedded
   `![alt](asset:<id>)` refs; `GeneratedPictureImage.block` is a render-ready convenience for
   direct consumers, never a persistence payload.
