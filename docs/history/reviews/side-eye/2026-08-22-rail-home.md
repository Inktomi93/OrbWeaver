# side-eye — HOME (rail sweep 1/10)

**Lane:** rail-home · **Surface:** home screen, live dev stack (`:5173` / `:8788`), read-only
**Verdict: SHIP WITH FIXES.** Nothing here blocks a user. Home is the most carefully written surface
in the app and its accessibility skeleton is genuinely excellent — I attacked it for a full battery
and the a11y, contrast and reading-surface layers held. What it does have is a soft bottom third
(below-fold content with no cue, wrong type voice, prose weight) and a front-door action that
freezes the frame for a quarter second.

**Design health: 32/40 — "good" band.** Score is calibration only; every item below is filed
regardless of the band.

## Findings

### \[P2-1] 293px of home sits below the fold at 1280×800 with no scroll cue, and the cut lands mid-word

**Why it hurts:** at the most common laptop height, the last thing a user sees is a paragraph
severed mid-word ("…its contents get ind"). Below that line, invisible, are BOTH of the Databank
empty state's calls to action (`Add your first document`, `Open Databank →`) and the entire
"Not yet" region. An empty state whose only CTAs are off-screen is an empty state that teaches
nothing. There is no fade mask, no gutter and no `::after` cue, so the cut reads as a rendering
fault rather than "scroll for more".

**Receipt** (`snap --eval`, content scroller `overflow-y:auto`):

| Arm | clientHeight | scrollHeight | hidden | scrollbar gutter | mask-image | ::after |
| - | - | - | - | - | - | - |
| 1280×800 default | 752 | 1045 | **293px** | 0px | `none` | `none` |
| 1280×800 compact | 752 | 991 | 239px | 0px | `none` | `none` |
| 1280×800 reading | 740 | 1590 | 850px | 0px | `none` | `none` |
| 900×800 (stacked) | 752 | 1701 | 949px | 0px | `none` | `none` |

Rects at 1280×800: `Open Databank` top=819 (fold=800) · `section[aria-label="Not yet"]` top=883
bottom=1061. Shots: `reports/snaps/home-bare.png` (cut visible), `reports/snaps/home-tall.png`
(1280×1800, everything present).

**Fix:** `adapt: the home content scroller — receipt: a bottom fade mask (the repo already owns the
recipe — `globals.css`horizontal-overflow cue, scroll-aware`data-fade-end`) plus a re-measure
showing the Databank CTAs above the fold at 1280×800.` Note `scrollbar-gutter: 0` was measured
headless; confirm the real-machine `scrollbar-width: thin` rendering before assuming zero cue.

### \[P2-2] The front door's primary action freezes the frame for \~233ms

**Why it hurts:** "Resume" is the single most-pressed control on this screen. Input handling is
excellent (4ms delay), so the click *registers* instantly — and then nothing moves for a quarter
second. That gap between "I pressed it" and "something happened" is exactly where a user presses
again.

**Receipt** — `pnpm perf-meter / --click '[aria-label="Resume Example — The Ashen Spire"]'`
(`reports/perf-meter/perf-meter.json`):

```
longTasks 5 (total 791ms / worst 238ms) · blocking 176ms · click dur 24ms / delay 4ms
worst rAF gap 233ms · layout shift 0
```

Corroborated by `pnpm record` (`reports/recordings/home-resume.webm`, strip
`reports/recordings/home-resume-click1.png` — 6 tiles × 120ms): tiles 1–3 show a half-painted
intermediate (room art painted, transcript and list still absent) before tile 4 settles ≈360ms
after the click. Console during that window: `[drop] 167ms rendered frame mid-animation · <html> · [data-slot=theme-scope] · aside[aria-label=Chats list]` and `[perf] slow commit region:content
106ms (update)`.

**Caveat, stated:** dev build, unminified, HMR-instrumented — the absolute numbers are inflated.
The *shape* (a long unpainted intermediate on the primary nav) is not a dev artifact.

**Fix:** `optimize: the home→room transition — receipt: perf-meter worst rAF gap under 100ms and a
record strip whose first post-click tile already carries the transcript skeleton.`

### \[P2-3] Home visibly re-settles on every load, and CLS under-reports it

**Why it hurts:** the landing surface reflows after the queries land — sections lift and the roadmap
block jumps a third of a viewport. The CLS *score* is green and will keep being green, because the
elements doing the moving are 1px separators and off-fold sections; the score is not measuring what
the eye sees.

**Receipt** — repeated across every boot, three independent runs
(`.cache/stack/client.log`, and `__orb.motion()` via `motion-audit`):

```
[cls] shift 0.0192 unexpected
   · [role=region] moved 0px,-24px
   · section[aria-label=Not yet] moved 0px,-155px
   · [role=region] moved 0px,-32px
   · [data-slot=separator] moved 250px,749px
   · [data-slot=separator] moved 180px,350px
   CLS 0.0202 (virtualized 0.0000) · observed 0.0202
```

`pnpm motion-audit /`: `cls-non-virtualized=0.0063`, `dirty-animations=0`, `dropped-frames=0%`.
So: **the numbers pass and the motion is compositor-clean — the composition is the finding.**

**Fix:** `layout: the home right column's async sections — receipt: reserve intrinsic height for the
databank/notifications-fed blocks so the [cls] line names no mover above ~8px.`

### \[P3-1] Two different focus-ring recipes on one surface

Every control on home focuses with the outset halo
`oklch(0.132 0.006 60) 0 0 0 2px, oklch(0.72 0.175 52) 0 0 0 4px` — except the six chat rows, which
use `oklch(0.72 0.175 52) 0 0 0 2px inset`. Same page, same keyboard walk, two visual languages for
"you are here". Nielsen #4.

**Receipt** — 24-stop keyboard walk, `fv=true` at every stop:

```
16 DIV    Resume Example — The Ashen Spire  686x136  bs=…0 0 0 2px, …0 0 0 4px  (outset halo)
18 BUTTON Traveler                          686x50   bs=oklch(0.72 0.175 52) 0px 0px 0px 2px inset
19 BUTTON Example — Midnight Run            686x50   bs=… inset
…23 BUTTON Example — The Bench After the Rift        bs=… inset
24 BUTTON Go to Chats                       82x32    bs=…0 0 0 2px, …0 0 0 4px  (outset halo)
```

**Fix:** `polish: the six chat rows in "Other rooms" — receipt: a focus walk whose box-shadow string
is identical in kind at stops 16–24.`

### \[P3-2] `[data-slot=card-root]` animates `background-color` — the app's own flagger scores it OVER BUDGET, and it contradicts motion-guide §3.7

**Receipt** — fires on interaction, captured by `pnpm record`:

```
[anim] animating non-compositor backgroundColor (guide §3.7 — transform/opacity/filter only)
   · [data-slot=card-root] · OVER BUDGET · route /
```

Source: `packages/ui/src/primitives/card/variants.ts:34` —
`cursor-pointer transition-colors duration-(--motion-fast) ease-out-expo hover:bg-accent active:bg-accent/80 …`.
`transition-colors` expands to include `background-color`.

**This is a COLLISION, not a defect call I get to make alone.** `motion-and-animation-guide.md`
§3.7 reads "Animate `transform`/`opacity` (and the Tailwind v4 standalone `scale`/`translate`)
only". A hover colour transition on an interactive card is paint-only (no layout) and is the most
conventional affordance feedback there is — but it is shipped in a *core `@orb/ui` primitive*, so
the flagger prints OVER BUDGET on every interactive-card hover anywhere in the app. Either §3.7 is
over-broad for paint-only colour, or the primitive must change. **State the fork; don't silently
pick an arm.**

### \[P3-3] `label-content-name-mismatch` on the ⌘K button — plus six axe FALSE POSITIVES, do not forward the count

Lighthouse (desktop + mobile) fails `label-content-name-mismatch` with 8 / 7 items. **Triaged:**

| Node | Verdict |
| - | - |
| `⌘K jump` topbar button | **REAL.** Visible text computes to `"⌘Kjump"` — no separator between the `<kbd>⌘K</kbd>` and the `<span>jump</span>` — so it is not a substring of the name `"⌘K jump — the command menu"`. WCAG 2.5.3 in letter |
| 6 × chat-row buttons | **FALSE POSITIVE.** These use the textbook pattern: `aria-label="Example — Midnight Run"` + `aria-describedby="…-subtitle …-meta"`. axe flags the row because the *visible* text node also carries the subtitle and timestamp. The rows are correctly built |
| Resume card | **BORDERLINE-PASS.** Name `"Resume Example — The Ashen Spire"` does contain the visible title; the extra visible text is the snippet |

**Fix:** `clarify: the ⌘K topbar button — receipt: a whitespace-separating node (or the name reworded
to contain the rendered string) and a Lighthouse run with label-content-name-mismatch at 1.0.`
Everything else here: **do not "fix"** — you would break a correct pattern.

Full report: `reports/lighthouse-home-desktop/report.json`, `reports/lighthouse-home-mobile/report.json`.
The other failing audit, `is-crawlable`, is a deliberate noindex on a local-first app — dismissed.

### \[P3-4] The hero is a `div[role=button]` while every sibling row is a real `<button>`

`<div aria-label="Resume Example — The Ashen Spire" role="button" tabindex="0" data-home-hearth="chat_…">`.

**I tested it before filing, and it works:** both Enter and Space activate it (`__orb.shell()` goes
`section:"Home", chatOpen:false` → `section:"Chats", chatOpen:true` after each). So this is a
robustness/consistency note, not a defect — a native `<button>` gets that behaviour for free and
cannot regress it.

`Calamity, Doomblade of…` wraps to two lines and truncates; `Elias Thorn` occupies one; `Birdie Mae

**Fix:** `polish: the character quick-pick name band — receipt: a fixed two-line reserved band so

### \[P3-6] "Not yet" roadmap prose is set in the 10.5px micro/gloss voice

Measured font sizes in that block: kicker 11px, item title 13px, **description paragraph 11px**,
mono status line 11px. `--text-micro = 0.65625rem = 10.5px` (`packages/ui/src/styles/theme.css:146`).

This is **not** a token violation — `--orb-tier-row-gloss-size: var(--text-micro)`
(`styles/tiers.css:30`) sanctions gloss at micro. It is a *voice* misuse: micro is for labels and
one-line glosses, and this block uses it for two-line explanatory paragraphs, twice, so the
description is the same size as the section kicker above it. Contrast is fine (8.45:1) — it is
small, not dim.

**Fix:** `typeset: the "Not yet" item descriptions — receipt: the gloss steps up one ramp stop and
design-audit stays clean on the type-ramp family.`

## ARIA-navigability recommendations

The a11y skeleton here is the best in the app. Concrete items only:

1. **`⌘K jump` button** (`div.shell-topbar-trail > button`): insert a separating text node (or a
   space in the `<span>`) between the `<kbd>⌘K</kbd>` chip and `jump`, so the rendered string
   `"⌘K jump"` is a literal substring of the accessible name. Today it computes to `"⌘Kjump"`.
2. **"Not yet" item titles** are `<p>`, not headings — `Buddy` and `Automation` read as body text
   with no structural distinction from their own descriptions. Promote to `h3` inside the region,
   or wrap the pair in a `<dl>`. (The region itself is correct: `<section aria-label="Not yet">`
   resolves to `role=region`.)
3. **Chat-row buttons** already do the right thing (`aria-label` = title, `aria-describedby` =
   subtitle + meta). **Leave them alone** — the axe finding against them is a false positive, and
   "fixing" it would delete a correct pattern.
4. **Hero card:** swap `div[role=button][tabindex=0]` for a native `<button>`. Behaviour is
   currently correct (Enter and Space both verified) — this protects it from regressing.
5. **Skip link:** raise to ≥24×24 in both arms (desktop 94×18, mobile 26×44).

**Verified working, do not touch:** skip link → Enter → focus lands on `<main aria-label="Home
content">` (measured); `aria-current="page"` on the active rail item (so section identity is NOT
colour-only — see retraction R-A); `navigation "Primary"` / `banner` / `main` landmarks; 7 named
regions each labelled by its own `h2`; `list`/`listitem` structure on both collections;
`alt=""` on decorative portraits with the name carried by the button; Lighthouse a11y **100** on
both desktop and mobile across 26 applicable audits (`color-contrast`, `target-size`,
`heading-order`, `landmark-one-main`, `tabindex`, `aria-*` all 1.0).

## Taste & flow verdict

**Does it look like shit? No — this is the best-looking surface in the app, and I went looking.**
The warm near-black, the single Ember accent, the ratified kicker+hairline section rule, the
character art at real 1:1 with no distortion: it reads as *made*, not generated. It trips none of
the §6 slop tells — no gradient text, no icon-tile stack, no generic indigo, no cream palette, no
bounce easing, no flat type hierarchy.

**Where the eye actually catches:**

- **The right column outruns the left and then dies below the fold.** Left column ends at y≈830
  (the "Elsewhere in the house" chips); right column runs to y≈1061. At the default 800px height
  the user sees the right column severed mid-sentence and the left column ending in air. At
  1280×1800 (`home-tall.png`) the imbalance is stark: \~740px of pure void under the left column.
  The two columns are not sharing the load.
- **Six kicker+hairline units on one screen** (PICK UP WHERE YOU LEFT OFF · OTHER ROOMS · ELSEWHERE
  IN THE HOUSE · START WITH · TEMP CHAT · DATABANK · NOT YET — seven, actually). Individually the
  kicker voice is ratified and good. Seven of them in one viewport is a drumbeat, and it flattens
  the difference between "here is your most important thing" and "here is a footnote about an
  unbuilt feature".
- **The right column is a wall of small explanatory prose.** Temp chat: 3 lines. Databank: 2 lines.
  "Not yet": four paragraphs at 10.5px. That is a lot of reading on a surface whose job is to get
  you *out* of it and into a room.
- **The hero has no art at the width most people run.** Retraction R-F establishes the mechanism is
  correct and deliberate. The *product* consequence is still worth an owner glance: the two-column
  split caps the left column at 686px, which sits just under the art threshold, so the
  emotional centrepiece of the front door is portrait-less at 1280 and portrait-ful at 1440. A user
  dragging a window edge watches the art pop in and out. The question is not "fix the mask" — it is
  "should the hero column be wide enough to earn its art at 1280?"
- **Reading arm** (`home-reading.png`, fontScale 1.25) holds up genuinely well — the quick-pick grid
  drops 3→2 columns cleanly. It does leave \~110px of dead gutter on the right where the 2-column
  grid doesn't expand to fill.

**Does it flow weird? No — the flow is the best thing here.** Eye lands on the h1 greeting, drops
straight to a hero card whose title, snippet, cast and RESUME arrow are all in one glance, then to a
recents list, then out. That is the correct task order for a returning user and it is executed
cleanly. Mobile (`home-mobile.png`) is arguably better than desktop: the bottom tab bar is labelled,
the tabs are 108×56, and the resume card gets full width.

**One home per concept — the IA lens:** `Elsewhere in the house` (8 labelled chips) duplicates the
8 non-home rail sections exactly. **I am calling this sanctioned, not a defect:** the rail is
icon-only, and this row is its labelled legend on the one surface where teaching belongs. It earns
its place. No other duplication found — the shell anatomy (§14) is respected: home declares BOTH
panels unavailable by design (`section-registry.ts` header: "a pane-less section (home declares
both)"), and it correctly claims `rail.brand` rather than minting a tenth rail slot.

**Is it intuitive cold?** Yes. From the screenshot alone a first-timer can name what this is and
what to press. "Seven rooms, still warm." tells you what you have; "Pick up where you left off"
tells you what to do; the character faces tell you what this app is *for*. That is a hard thing to
do in one viewport and it is done.

**The one thing I'd change if I could change one thing:** cut or relocate "Not yet". A roadmap of
unbuilt features, set in the smallest type on the page, below the fold, behind four other kickers,
is the least-read real estate on the screen carrying the most words. Removing it fixes the fold
problem, the prose-weight problem and the type-voice problem in one move — and gives the left
column's void something to balance against.

## What's genuinely working (do not touch)

1. **The copy, and the thinking under it.** `home-masthead-body.tsx` counts the server census, not
   the page — its header records that counting `items.length` once told a user with exactly eight
   rooms "Eight rooms and more, still warm." about a house with nothing else in it. Numbers spelled
   to ten, `"An empty house."` for zero, the subtitle vanishing entirely rather than printing "You
   left off never". This is the standard the rest of the app should be held to.
2. **The accessibility skeleton.** Skip link that actually lands focus on `<main>`; landmarks;
   7 regions each labelled by its own `h2`; `aria-current="page"`; name-plus-describedby on every
   list row; `alt=""` on decorative art; a 24-stop keyboard walk with `:focus-visible` true at
   every single stop; Lighthouse a11y 100 on both devices.
3. **Contrast, and the reading-surface guarantee.** Thirteen text roles measured, **zero FAILs**,
   range **7.65:1 – 17.14:1** (h1 17.14, hero snippet 13.23, muted glosses 8.45, "Game" badge 7.65)
   — and it holds in the Light arm too (h1 15.56, snippet 14.43). The art-bleed can't reach prose by
   construction, not by vigilance: the band starts one `--reading-measure` + one `--spacing-section`
   in, and its mask peaks at 0.55. That is a mechanism, not a promise.

---

## The single biggest opportunity

**Reclaim the bottom third of the right column.** Three separate findings (P2-1 below-fold cue,
P3-6 wrong type voice, and the taste call on prose weight) all converge on the same 300 vertical
pixels. Cut "Not yet" or move it behind a disclosure, lift the Databank empty-state CTAs above the
fold, and let the left column's void close up — one edit, three findings, and the front door stops
looking severed at 1280×800.
