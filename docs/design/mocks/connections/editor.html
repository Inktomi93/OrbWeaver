ONE row grammar serves both blocks, and that is the decision. declared and features are different schemas with the same reading job — what is the resolved value, where did it come from, can I change it — so they get the same three-part row: key (mono, the schema's own word, because these are the two blocks where a user IS looking at machine vocabulary) · resolved value + source line · one Override per field. An overridden row changes colour, restates the value it replaced in the source line, and swaps Override for Reset. That is what makes the block honest: the thing you overrode is never hidden by the override.

What this server accepts is written in USER words; Endpoint quirks is not. Capability has plain equivalents that lose nothing (window → context window, modalities → takes / gives back, pricing → price), so it uses them. A quirk does not: prefill: continue-final-message IS the vocabulary of the server's own docs, and translating it would make the one block whose whole purpose is matching a server's documentation impossible to match against it. §5.3a already calls Endpoint quirks “a diagnostics surface, not a setup step” — this is that sentence in layout. But the rationale reaches the VALUE, not the key, and the key column is corrected accordingly. An earlier draft rendered seven raw camelCase identifiers (prefillSuppressesThinking, reasoningKeys, rerankPath…) and justified them with matchability — which those exact rows falsify, because they are our own features schema's TypeScript property names and vLLM's documentation contains no such string. The rule: a quirk key stays RAW only when that exact string is the wire's; otherwise it is written in plain words and the wire's string stays where it always was, in the value. So prefill survives verbatim — it is §5.3a's worked example and a real wire technique — and its value is still continue-final-message; reasoningKeys becomes reasoning fields over the unchanged value reasoning, reasoning_content, which is what a reader actually greps a server's docs for. Nothing matchable was lost; seven schema identifiers left the user surface.

Why read-only-by-default is the right default and not timidity. Every line in both blocks has a correct value already — measured, reported, or from the provider row. An editable field invites the user to answer a question they have no way to answer better than the system did, and a wrong answer here does not fail loudly: it produces turns that quietly drop a knob or 400 on the fifth message. Override is one click away and per-field, so the user who genuinely has a weird box (the reason this schema exists) is not blocked — they just have to mean it.

The Override control is a BUTTON, not a switch or an inline input. It has to be the thing that reveals an editor rather than the editor itself, because the shape of the editor differs per field (a number, an enum, a string list, a boolean) and a row that sometimes contains a text box and sometimes a select is a row with no rhythm. Clicking Override replaces the value line with the right control in place, which is why the row reserves its own height rather than letting the source line collapse.

THE 486 ANSWER: yes, the editor fits — because the editor is ONE COLUMN at both widths and the tiers do the work. FIVE things reflow, each drawn in boards D–F (an earlier draft of this note claimed three, counted two of them as one, and never drew the last two at all): (1) the resolved-fact ROW stacks — the mono key takes its own line, the value and source follow, and the Override button moves to a right-aligned line of its own, because the row's 172px key basis plus a mono value plus a 26px-tall button cannot share a 462px content line without the source wrapping to three (Board E); (2) the EXTRAS key/value pair stacks, which is why the grid carries visible Field / Value column headers — two identical mono boxes one above the other are unreadable without them (Board F); (3) the two-up transport pair (Extra headers / Don't send these fields) becomes one-up — its flex: 1 1 240px crossover is at 490px of content (measured by sweeping the body 900→380px in 4px steps: side-by-side down to a 532px body, one-up at 528px), so 486 is comfortably below it and above it nothing moves (Board F); (4) the capability badge rail truncates — greens first, so the rail shows what the connection CAN do and summarises the rest as …and 4 more it can't serve (Board D); (5) the tier count badge shortens, 3 fields overridden → 3 overridden, because the header has to hold a chevron, a title and a badge on one line and the long form pushes the badge to a second row. A collapsed tier keeps its kicker summary at 486 — abbreviated (vLLM · 127.0.0.1:8000 rather than the 870 form with the model), truncating rather than pushing, and dropped entirely on a tier that carries a count badge, which is the denser summary. 486 is the width WITH the context panel open, i.e. where a user is comparing this pane against a room; a collapsed tier that is a bare word and a chevron is exactly the wrong thing there. What does NOT change is the important part: the default state at 486 is still four fields and one verdict line, because the two heavy tiers are collapsed, and collapsing is width-independent. The editor fits at 486 by construction, not by squeezing — which is the whole reason §5.3a specified the tiers before the schema.

The picker's groups are the four auth kinds and that is not a coincidence — it is the only grouping that answers the question the user is actually asking, which is what am I about to be asked for: a key, a URL, a sign-in, or nothing. Nine built-in rows in four groups; a plugin provider joins the group its own auth names, so the picker never grows a fifth heading by accident. An unavailable row renders disabled with its reason as the gloss, never hidden — §5.3a's point about runtime-missing is that a cause code is not a sentence a person can act on, so the row says “The Claude runtime isn't installed on this server.”, which is the string connections-model.ts:79 already ships. Hiding the row instead would leave a subscription user looking for an option that is not there and no way to learn why. The grouping is a REAL group, not a visual one. Four divs styled as headings inside a role="listbox" give a screen-reader user nine flat options — the exact outcome §5.3a wrote the grouping to prevent — and, being non-option children of a listbox, they get folded into the listbox's own accessible name (measured: listbox “Hosted (key) OpenRouter Anthropic OpenAI Your own server (URL)…”). Each group is a role="group" with aria-labelledby pointing at its heading, the listbox carries an explicit aria-label="Provider", and the heading sits at the ratified text.micro floor of 10.5px rather than the 9.5px it was drawn at — which is below the ramp and is the weakest channel the grouping had.
