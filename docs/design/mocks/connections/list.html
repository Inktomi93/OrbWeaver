Shell-anatomy answer (the §5.3a question). No collision, under four rules the build keeps: (1) the row is flat inside the section — no card, no border-radius frame, no leading selection bar; a card-in-a-card and a left accent stripe are LIST-PANE anatomy and inside a settings body they read as a second nav. (2) the section header owns exactly ONE action (Add a connection) and the row owns exactly one (the kebab), so the settings body never has two competing trailing actions on one line. (3) the row's only inline control is the Allow background work switch — it is there because §5.3a makes the Model-roles slot refuse a background binding and offer this same switch, and a user who lands here from that refusal must find it without opening an editor. (4) nothing in the row is a link into another shelf — the kebab's Edit opens the editor in this same body (mock 2).

Task badges use the ROLE words, never the schema word. task is SEALED (§5.3a); the badge text is the Model-roles label. A row shows the roles it CAN serve, and the capability-derived ones only — a badge is a statement about the model, not about what the user bound. Two non-role badges ride the same rail because they are the same size class and the same reading job: 3 fields overridden (the declared_overrides_measured home §5.3a names — "a badge on the connection row … NEVER the turn stream") and Model not in list (the modelListed: false tell, whose full sentence lives in the editor, mock 2).

Why the sweep action is a MENU item and not a row button. "Use this connection for everything it can serve" writes up to six user bindings in one act — it is the most consequential thing on this pane and the least frequent. A button on every row would make the pane's loudest affordance its rarest one; the menu keeps the row scannable and still puts the action one click from the row it acts on. Its gloss NAMES the roles it will write, so the undo is knowable before the click rather than after it (there is no default to fall back to — §7.2 F2/F16).

They become Not set, and there is no default model, so those turns stop until you pick something else. Past messages keep their attribution. The key “work” stays in Saved keys. This can’t be undone.

The dialog ships; only its DESCRIPTION changes. connections-list-section.tsx:138 already renders the house ConfirmDialog with “Every role using this connection goes unset until you pick another. Past messages keep their attribution. This can’t be undone.” That sentence is correct and unquantified — it cannot tell a user whether they are about to break one role or five, which is the only thing they need in order to decide. The proposal is the count and the role names, plus the one fact the shipped copy omits: the CREDENTIAL survives (§5.3 — a connection is deleted, its key is a separate row, and a user who thinks removing the connection revokes the key will not remove it). An earlier draft of this board put the confirm INLINE in the row on the argument that a modal covers the roles it names; that is answered more cheaply by naming them in the description, and replacing the house confirm primitive for one surface is a cost with no remaining benefit. Drawn here as it ships, because §5.3a’s word is “confirmed remove”, not “a new confirm”.
