LAW LIST = sessions with the character as row identity (D62 §2b.1 "past refinery sessions per character"; addendum §10.5-3 rules the drill store has ONE primary, so the roster is flat and the character rides the row). Row cargo = refinerySessionSummarySchema: name (nullable → "Untitled session") · character · latestVerdict (null → "No verdict") · iterationCount · updatedAt. CONTEXT = the cross-run ledger (addendum §10.3): Runs + Setup, nothing the CONTENT frame already says (the anti-echo rule). Run rows carry the contract's real provenance — model, promptTokens/outputTokens, iteration — and strippedKeys becomes the visible warn line rather than a silent success. Stage is NOT a drill — the stepper is in-session UI state (addendum §10.2), so the phone back gesture pops to the roster, never stage-by-stage. The anti-drift line under the character name is the originalCard anchor stated in the UI, because it is the invariant the whole feature sells.

FORK A · assay density Drawn: the selected field row expands its strengths/weaknesses/suggestions inline; the rest collapse to name + bar + score. The alternative is every row always expanded (a long scroll, everything comparable at once) or a master/detail split (list left, critique right). Rec: accordion-with-one-open as drawn — the payload allows 4 000 chars per critique string × 3 per field, which no always-expanded list survives.

FORK B · where "priority improvements" lives Drawn as a second column beside the assay. Alternative: a strip directly under the summary gauge (full width, above the per-field rows), which reads more like "here is what to do next" and less like a sidebar. Rec: as drawn at wide widths, folding under the gauge below the CONTENT breakpoint.

LAW Accept state is per-BLOCK and the Accept-all row carries an indeterminate arm — that is the shipped CompareBlocks contract (accepted[] / onAcceptedChange), not a new control.

LAW The greeting block is addressed by index (greetingIndex) — orb greetings are ONE array, and the payload's greetingIndex is present ⇔ field === "greetings".

FORK C · which instrument per block Drawn BOTH ways in one frame: CompareBlocks pairs for prose fields, an inline DiffView for the greeting (short text, where a word diff is legible). The "side by side / inline" segmented control makes it a per-user choice. Rec: ship the toggle, default side-by-side for fields over ~200 chars and inline below it.

FORK D · apply from the compare, or a confirm step? Drawn: the accept set IS the apply set, one button, no dialog. Alternative: "Review apply" opens a modal listing the accepted fields before writing. Rec: as drawn — apply already auto-snapshots ("auto: before refinery apply") and the result panel itemises drops, so a confirm modal buys nothing but a click.
