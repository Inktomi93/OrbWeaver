# Plugin distribution (#1238) — the teaching-plugins package + three install doors

> **Commission (owner rulings, verbatim, 2026-09-02).** (1) *"our seeded teaching plugins are not in an easy to reach place and they rot — make a new package for them, like we did with tooling."* (2) *"not forcing folks to zip them."* (3) *"chrome style where you can load unpacked or install from a github by git cloning into a directory in the app — the app does the clone like sillytavern."* (4) Final door set: *"load unpacked and folder upload like we already have with our import shit and then an install from github that clones."* (5) Mid-design, on a separate confirm step for the clone door: *"maybe just a disclaimer text? no separate click."* (6) Mid-design, on container-time asset copying: *"if dockerfile which we don't even use yet is moving default assets around that's a nah from me dog — that's crunchy and fragile."* — default content ships in the workspace and arrives at runtime through the app's own doors; a container adds nothing but a filesystem.

Reference implementation, verified: SillyTavern `src/endpoints/extensions.js` — install = server-side shallow clone of a pasted URL (`{depth:1}`, extensions.js:134-138) into an app-owned per-user/global dir, name = sanitized repo basename with a 409 on collision (:122-131), post-clone `manifest.json` read with atomic rollback (`rm -rf` the clone on a bad manifest, :141-151); update = fetch/pull reporting the short commit hash + up-to-date (:193-210); http/https protocol check (:106); distribution = plain git repos, no packing anywhere.

This document is the build authority for #1238. Zero production code lands with it; §9 is the dispatch plan.

## 1. Before-state (receipts)

- **The teaching plugins live inside the server package's entry tier**: `packages/server/src/entry/boot/seed-assets/plugins/<slug>/{manifest.json,main.js,ui.js?,ui/assets/*,README.md}` — nine of them (`EXAMPLE_PLUGIN_SLUGS`, `packages/server/src/entry/boot/seed-example-plugins.ts:42-52`), plus the published SDK mirror `host-v1.d.ts`. The authoring README's own copy loop is `cp -r packages/server/src/entry/boot/seed-assets/plugins/oracle-deck …` (`seed-assets/plugins/README.md`) — five directories deep in a tier no plugin author has business reading. That is the "not easy to reach" half of the ruling.
- **The rot mechanism is structural, not neglect**: the guest sources are `.js`, and `allowJs` is `false` repo-wide (`tsconfig.base.json:72`), so **no type program in the repo checks a single line of the nine `main.js`/`ui.js` files**. The only pinned artifact is the SDK mirror, held assignable against `@orb/contracts/plugin` by `tests/contracts/plugin/host-v1.test-d.ts` — the mirror is checked; the plugins that use it are not. An API change that breaks every seeded plugin is invisible until someone enables one.
- **Seeding packs at runtime**: `packSeedPluginBundle` (`packages/server/src/entry/boot/seed-assets/index.ts:94-120`) zips the admitted entries (fixed mtime `:62` for byte-determinism) and the per-user seeder drives the REAL `install` + `setGrant` verbs — installed, disabled, zero grants, standing re-consent ask (`seed-example-plugins.ts:10-17`, same posture as admin distribution, `domain/plugin/substrate/distribution.ts:5-16`). `scripts/pack-plugin.ts` emits distributable zips through the same packer.
- **Before-state finding (per ruling 6):** today's flow depends on image-build asset copying — the sources sat in server src explicitly *"so they ride the same `packages/server/src` COPY the image already makes — a repo-root `examples/` directory would not exist at runtime"* (`packages/server/src/entry/boot/seed-assets/index.ts:1`, whose header now records the move; the copy is `Dockerfile` app-files stage). The demo-chat and avatar seed assets share this pattern. This design removes that dependence for plugins (§2); the sibling asset families are out of scope and named here as the same class.
- **Two install doors exist today**, both landing in the ONE source-agnostic funnel: a zip dropzone (client preview `features/plugin/lib/plugin-bundle.ts:1-25` — explicitly a display read, not a trust boundary) and a URL fetch through the egress guard (`domain/plugin/verbs/install-from-url.ts:23-28`, preview via `preview-from-url.ts:18-24`). The funnel is `domain/plugin/substrate/manifest.ts` (`parseBundle`, unzip hardening + bomb caps + schema, header `:1-40`), and the law is written on it twice: *"a new origin is just another byte source, never a re-shape or a second install path"* (`@orb/contracts/plugin/lifecycle.ts:6-8`; `substrate/manifest.ts:2-4`).
- **Update machinery exists for the url origin**: `checkForUpdates` (re-fetch manifest, leak-free `unreachable` collapse, `verbs/check-for-updates.ts:1-16`), `upgradeFromStoredUrl` (owner-load before any fetch; re-consent wall on widened reach rides `upgrade` unchanged, `verbs/upgrade-from-stored-url.ts:1-17`).
- **Folder upload precedent**: `@orb/ui`'s `FolderPicker` (`packages/ui/src/primitives/file-dropzone/folder-picker.tsx:18-23`, `webkitdirectory`, files carry `webkitRelativePath`), consumed today by the Backup & Restore import pane (`features/workloads/components/import-library-section.tsx:1-17`) — the owner's "like we already have with our import shit".
- **Authority model is settled**: D147 — plugins are user-scoped; ownership of the row is the entire authority model; server-wide = an admin-triggered fan-out of per-user rows via `installForAllUsers`; enable is the consent act and cannot be performed on someone's behalf.
- **Manifest home is settled**: `@orb/contracts/plugin/manifest.ts` (`pluginManifestSchema:228-276`, capability axis `:13-98`, bundle-entry vocabulary `:183-191`). The full validated manifest is persisted per row (`substrate/manifest.ts:61-63`); `version` is already the semver that drives upgrade ordering (`:308-334`).

Priors consulted (shared memory, by filename): `plugin-node-kind-coupled-sites`, `plugin-tool-wire-name-is-one-mint`, `guest-vocabulary-subset-is-a-type`, `plugin-consent-is-reach`, `enable-is-the-escalation-not-the-read`, `plugin-fetched-cas-write-is-a-referencing-row`, `tooling-one-home-no-shortcuts`, `fflate-zip-mtime-timezone-fragile`, `kit-decompressionstream-gotchas`, `new-doc-catalog-two-commit-stack`, `axis-home-follows-reachability`, `workspace-package-sideeffects-field`, `new-router-needs-sweep-classification`.

## 2. Decision 1 — `@orb/showcase-plugins`, a runtime workspace package under `packages/`

> **LANDED 2026-09-05 (#1692), with one deliberate carry-forward.** The package exists at
> `packages/showcase-plugins/` and owns the nine bundles, the authoring guide and the published `host-v1.d.ts`;
> `@orb/server` declares it and the seeder resolves `packShowcaseBundle` by node resolution. The `checkJs`
> program over the guest sources — the ROT half of this section — did NOT land with the move and is its own
> row: turning nine never-compiled `.js` files into a type program is a behaviour change, and the move is
> byte-identical on purpose (pack-hash pin, `tests/showcase-plugins/index.test.ts`).

**The teaching set becomes a real workspace package that `@orb/server` depends on, and the seeder reaches it by node resolution — no copy step, no generated mirror, no container involvement.**

- **Location: `packages/showcase-plugins/`** (name fork F1, §8). NOT a root-level sibling of `tooling/`: `tooling` sits ABOVE the cake because nothing in `packages/*` may import it; this package is CONSUMED AT RUNTIME by the server's seeder, so its home follows reachability — below `server` in the cake, beside `contracts`/`db`. The `packages/*` workspace glob admits it with zero `pnpm-workspace.yaml` membership edits. The owner's "like we did with tooling" is honored in its mechanism (a first-class workspace package with its own manifest, tsconfig, and type program) — the position differs because the consumer differs.
- **Contents**: the nine plugin directories move verbatim (`<slug>/{manifest.json,main.js,ui.js?,ui/assets/*,README.md}`), the authoring `README.md`, the SDK mirror `host-v1.d.ts` (its new one home — it is the author-facing public API surface and belongs beside the code that models its use), the packer (`packSeedPluginBundle` + `PLUGIN_BUNDLE_MTIME_MS` + `readBundleAssets` move out of `seed-assets/index.ts` — the packer's home follows the content), and a small typed index exporting `SHOWCASE_PLUGIN_SLUGS` (the renamed `EXAMPLE_PLUGIN_SLUGS` tuple) and `packShowcaseBundle(slug)`.
- **Dependencies**: `@orb/contracts` (the bundle-entry constants + `pluginManifestSchema` the packer already imports) + `fflate` (`catalog:`). Nothing else. **This is the living proof the public plugin API is self-sufficient**: the package compiles against the PUBLISHED `host-v1.d.ts` plus contracts' public plugin exports and nothing server-internal. Manifest: `engines >=26`, correct `sideEffects` (memory: `workspace-package-sideeffects-field`).
- **The rot fix — the guest sources enter a type program**: the package's own `tsconfig.json` sets `allowJs`+`checkJs` with `host-v1.d.ts` ambient, so all nine `main.js`/`ui.js` files typecheck against the published SDK on every `pnpm typecheck` (the per-package program is the owner; the root aggregator picks up the package's `.ts` index via its existing `packages/*/src` include and, with `allowJs:false` there, ignores the `.js` guests — no aggregator change). A host-API change that breaks a seeded plugin is now a red `tsc`, and the mirror-drift test keeps its pin (retargeted path).
- **Authoring language stays plain `.js` + JSDoc against the d.ts** (fork F2, §8 — default). The published authoring model IS "copy `host-v1.d.ts` next to your `main.js`, no build step" (`host-v1.d.ts:1-16`); the teaching set must model the story we publish, and with no emit step the bytes a user reads in the seeded pane are the bytes we authored — one artifact, zero emit skew. Rejected: author in TS + `tsc`-emit `.js` — real syntax, but the shipped artifact loses the annotations that teach, and it forks the teaching material from the published authoring model.
- **Runtime wiring**: `entry/compose/services.ts:1111` flips its `packBundle: packSeedPluginBundle` import to the package; `seed-example-plugins.ts` imports the slug tuple from the package. `seed-assets/plugins/` is DELETED in the same change (no old-beside-new). Dev, bare-metal prod, and any future container all resolve the package identically through `node_modules` (pnpm's workspace link / `pnpm deploy` materialization) — ruling 6 satisfied: the container adds nothing but a filesystem, and no design element hangs off an image build step.
- **Rejected alternatives**: (a) root-level `plugins/` dir above the cake with a build that copies bundles into `seed-assets/` — a generated committed mirror plus a freshness gate plus image-copy dependence; ruling 6 kills it, and the workspace-dep shape makes the entire copy pipeline unnecessary. (b) Server reads a repo-root dir by relative path — breaks under any deployment that doesn't ship the repo root, which is exactly the fragility `seed-assets/index.ts:82-83` documents. (c) Leave content in server src and only add typechecking — fixes rot, leaves reachability broken; half the ruling.
- **Enforcers, named**: the package boundary is resolve-time physics (undeclared imports don't resolve); `client`/`ui` must not import it — a dep-cruiser layer rule in the same change; guest-source conformance = the package's own `tsc` program (`pnpm typecheck` per-package leg); mirror fidelity = the retargeted `tests/contracts/plugin/host-v1.test-d.ts`; seed-byte identity across the move = a one-time pin in the move lane (pack each slug before/after, hashes equal — the fixed mtime `:62` makes this exact).
- **Coupled sites (move-lane checklist, verified by sweep)**: `seed-assets/index.ts` (packer out; avatar/demo-chat readers stay) · `seed-example-plugins.ts` · `entry/boot/index.ts` · `entry/compose/services.ts:1111` · `scripts/pack-plugin.ts` (import + USAGE path) · `packages/server/tsconfig.json` (the d.ts exclude row dies) · root `tsconfig.json` (the explicit d.ts include row retargets — the test-d needs its globals in the graph program) · `tests/contracts/plugin/host-v1.test-d.ts` · the three gates that carve out the seed path by literal: `tooling/src/verify/gates/{brand-in-name-position,test-presence,no-inline-union-redecl}.ts` + `tests/tooling/verify/gates/test-presence.int.test.ts` · `tests/server/entry/boot/seed-example-plugins.int.test.ts` + `tests/server/entry/boot/seed-atlas-realm-dates.suite.test.ts` · Dockerfile package.json/app-files rows (kept honest, explicitly non-load-bearing per ruling 6) · knip workspace entry · `docs/design/plugin-showcase-set.md` + the authoring README's paths.

## 3. Decision 2 — door 1: load unpacked (dev-gated)

**A dev-only verb that points the server at a local plugin directory and runs it through the one funnel.**

- The packer generalizes: `packPluginDir(absDir)` (the moved packer parameterized on its base dir; `packShowcaseBundle` becomes its seed-slug wrapper). A new `plugin.installUnpacked { path }` verb packs the directory's admitted entries and hands the bytes to the EXISTING `install`/`upgrade` pair: slug absent → `install`; slug present → `upgrade` (an equal version is a legal re-install, `substrate/manifest.ts:322-327`, which is precisely the dev reload loop). Origin recorded as `"upload"` (no remembered URL — the honest arm of `lifecycle.ts:9`; a dev dir path is not a re-fetchable source and MUST NOT mint a new origin for one door's convenience).
- **Reload is load-once in v1**: re-invoke the verb to pick up edits. No file watcher, deliberately — a watcher is a persistent fs subscription with lifecycle and multi-user questions the dev loop doesn't need; the verb is idempotent-per-edit already.
- **Dev gate, enforcer named**: the verb refuses unless the server's env discriminant says non-production (`foundation/env` is the home; the client affordance rides `IS_DEV`, `packages/client/src/lib/dev-flag.ts:7`, the #1095 bug-button posture). The gate is BEHAVIORAL: an int test pins the production-posture refusal AND the dev-posture admission (both arms — a green that cannot fail proves nothing). The arbitrary-local-path read is admissible ONLY because of this gate; it is first on the security-review list (§6).
- Rejected: a separate "unpacked plugins" registry that serves from the live directory (the Chrome model taken literally) — a second guest-code store beside the CAS bundle, violating the one-funnel law for a convenience the pack-on-invoke shape already delivers.

## 4. Decision 3 — door 2: folder upload (no zip required)

**Pure client work: the plugin pane grows a folder arm that packs the picked directory client-side and rides the EXISTING preview → grant → install flow. Zero new server surface.**

- The install card (`features/plugin/components/plugin-install-card.tsx:1-30` — the two-step consent read) adds `FolderPicker` beside the zip dropzone. The picked `File[]` (paths in `webkitRelativePath`) is packed with `fflate.zipSync` — already a client dep, already imported by this feature (`plugin-bundle.ts:29`) — selecting EXACTLY the admitted entry spellings from the folder root: `manifest.json`, `main.js`, `ui.js`, `ui/assets/<name>` (first path segment stripped; everything else — README, .git, editor litter — ignored, the seed packer's own pack-what-you-know posture, `seed-assets/index.ts:125-128`). The packed bytes then flow through the UNCHANGED `readPluginBundle` preview and the UNCHANGED `install` mutation (`bundleBase64`).
- Traversal is unspellable, not filtered: the client packer EMITS only the four admitted entry spellings, and the server funnel re-judges every byte regardless (`plugin-bundle.ts:4-11` — the client is a display read, never the trust boundary). The 1 MiB compressed cap applies as today.
- Zip upload keeps working through the same dropzone, untouched.
- Rejected: a new server verb accepting a multipart/file-map upload — a second install path with its own validation surface, refused by the funnel law (`lifecycle.ts:6-8`); the folder is just another way to produce the byte source the wire already carries.

## 5. Decision 4 — door 3: install from GitHub (the app clones)

**The clone is external I/O → a new infra adapter `infra/git`. The clone is EPHEMERAL: it exists to produce bundle bytes for the one funnel; the CAS bundle + row provenance remain the only stores of guest code.**

- **Adapter**: `infra/git` exposes two compose-wired ops on `PluginContext` (the `ctx.fetchBundle` injection shape — the domain never imports infra to branch, `substrate/manifest.ts:344`): `fetchGitBundle(url) → {bytes, commit}` (shallow clone `depth:1`/single-branch to a scratch dir, pack the admitted entries via the ONE packer (`packPluginDir`, §3), `rm -rf` the scratch dir in a `finally`, return the zip bytes + resolved HEAD hash) and `remoteHead(url) → commit` (ref listing, no checkout — the clone-free update probe).
- **Git execution: `isomorphic-git` (pure JS), with its pluggable HTTP client wrapped over OUR egress validators.** The load-bearing receipt is that the clone's smart-HTTP requests then run under the SAME wall every other plugin fetch runs under — https-only, per-hop IP-literal/private-range denial (`infra/network/egress.ts:55-96`), redirect discipline, and a response byte budget in the wrapper — so the SSRF posture keeps ONE home instead of growing a git-shaped exception. Rejected: (a) system git via `execFile` — the runtime image ships no `git` binary (node:26-bookworm-slim; the Dockerfile installs only ca-certificates/curl), so it costs an image-level dependency ruling 6 just fenced off, and the clone's network behavior escapes our egress wall entirely; (b) `simple-git` (the ST choice, extensions.js:6) — a dependency ON TOP of the same binary requirement, the weakest arm here.
- **Ephemeral clone, not a persistent checkout (the deliberate ST divergence).** ST keeps the clone because ST serves extensions from disk; we serve from CAS. A persistent per-user clone directory would be a SECOND store of guest code (uninstall cleanup, quota, drift against the CAS bundle) and a second install path in all but name — the funnel law (`lifecycle.ts:6-8`) decides this. Ruling 3's mechanism is preserved: the app does the clone, into a directory in the app; the directory is just not the system of record, and ST's atomic manifest-or-rollback contract (extensions.js:141-151) comes free — nothing persists unless `parseBundle` + `install` accept the bytes.
- **Repo contract**: repo root = bundle layout (`manifest.json` + `main.js` + optional `ui.js` + `ui/assets/*` — committed built artifacts, the ST distribution model). The packer packs what it knows; a repo missing required entries fails with the funnel's own typed refusal. Name/slug authority is `manifest.id` (exactly as every other door — never the repo basename; ST's sanitized-basename naming is its trust edge, ours is the manifest, `contracts/plugin/manifest.ts:230`).
- **Origin + provenance**: `PLUGIN_ORIGINS` grows `"git"` (the axis is additive by design, `lifecycle.ts:6-16`; the db CHECK derives from the tuple and `plugins_source_url_check` is already written against `= 'upload'` so a URL-carrying origin passes unchanged, `db/src/schema/plugin.ts:106-113`). `sourceUrl` = the repo URL. NEW nullable column `plugins.source_commit` + CHECK (`origin = 'git'` ⟺ `source_commit` non-null) — the commit hash is the version receipt ruling 3 names. Pre-launch schema delta squashes into `0000_baseline` (db law).
- **Verbs mirror the url family exactly** (verb-to-verb delegation, no second safety story): `previewFromGit` (clone → pack → `parseBundle` → return manifest + commit; nothing persists — the consent read, `preview-from-url.ts` shape) · `installFromGit` (clone → pack → `install` with `{origin:"git", sourceUrl, sourceCommit}`) · `upgradeFromStoredGit` (owner-scoped row load BEFORE any clone — the `upgrade-from-stored-url.ts:10-17` ordering; re-clone the stored URL; `upgrade` applies the re-consent wall on widened reach unchanged) · a `git` arm in `checkForUpdates` (`remoteHead(sourceUrl)` vs stored `source_commit` → `update-available`/`up-to-date`; ANY failure collapses to the one leak-free `unreachable` arm, the `check-for-updates.ts:9-14` posture). Hash inequality, not manifest version, is the update SIGNAL (authors forget bumps; ST reports the hash, extensions.js:207-210); `upgrade`'s downgrade refusal on `manifest.version` still governs what may LAND.
- **URL policy — derived, not forked**: https-only, ANY host, private-range/IP-literal denial — exactly the existing `fetchBundle` posture (`substrate/manifest.ts:336-344`). No host allowlist: the URL door has none, and a second policy for the same reach class would be a fork of the SSRF wall's one home. Copy names GitHub as the primary example while accepting any https git remote (fork F3 default, §8 — ST's own shape).
- **Per-user vs deployment-wide**: rides D147 unchanged. A user's git install mints their own row under their own Principal; deployment-wide distribution stays the existing admin fan-out (`installForAllUsers` takes bundle bytes — an admin uses the git door's preview/clone to obtain bytes, then the existing distribution machinery lands per-user consent-first copies). Zero new distribution machinery.
- **Client**: the install card's third arm — repo URL field → `previewFromGit` → the SAME grant screen → `installFromGit`. Failure rendering copies the URL arm's leak-free single fixed line (no SSRF oracle, `plugin-install-card.tsx:14-21`). **Owner ruling 2026-09-02 (verbatim: "maybe just a disclaimer text? no separate click")**: inline disclaimer copy sits by the git URL field — this action clones and stores third-party code; capabilities are granted separately and nothing runs until enabled — and there is NO separate confirmation step; the consent moment stays exactly where every door's is (the grant screen at install, enable as the second explicit act). Disclaimer copy conforms to `docs/design/vocabulary-map.md`.

## 6. Security routing (thin by owner ruling)

The permission/consent model is already the trust story (owner, 2026-09-02: *"we kinda already have consent boundaries out the ass"*). **Every door in this design produces BYTES for the one funnel and lands through the unchanged `install`/`upgrade` verbs** — same `parseBundle` hardening, same grant ⊆ declared check, same consent surface (`plugin-install-card.tsx` two-step), same disabled-by-default landing with enable as a second explicit act (`verbs/install.ts:7-11`, D147). No new permission tiers, no trust levels for git sources, no signatures, no new consent UX.

What the build's security-executor review must cover (ingress mechanics only):

| surface | what to verify |
| - | - |
| `infra/git` http wrapper | every smart-HTTP hop passes the egress validators (incl. redirects), response byte budgets enforced, scratch-dir cleanup on every throw path, no shell anywhere, error collapse leaks no SSRF oracle |
| folder upload | client packs by the four admitted entry spellings only; server funnel re-judges (no new server surface to review beyond confirming there is none) |
| load unpacked | the dev gate's both-arm pin (prod refusal + dev admission); the arbitrary-path read exists only behind it |
| manifest parse | unchanged funnel; confirm the git door adds no parse surface beside it |

## 7. Migration + the manifest contract

**Nothing migrates.** Every installed plugin already carries its full validated manifest, `version`, `origin` and (for url) `sourceUrl` (§1). The `git` origin and `source_commit` are additive; existing rows are untouched. The manifest schema gains NO fields — the commit hash is row provenance, not a manifest concern, and `version` remains the one upgrade-ordering key. The teaching-package move changes seed BYTES not at all (pinned, §2) and seeded rows not at all (same verbs, same posture).
